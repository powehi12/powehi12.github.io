## 结论：Biomni 是真正的 Agent

**Biomni 不是一个单纯回答生物医学问题的聊天机器人，也不是一个新的生物医学大模型。它是一套“以大语言模型为大脑、以生物医学软件与数据库为工具箱”的通用科研 Agent 系统。**

它之所以属于 Agent，是因为面对一个研究目标时，它能够：

1. 判断需要哪些数据和工具；
2. 自动制定研究步骤；
3. 编写并运行 Python、R 或 Bash 代码；
4. 读取程序输出；
5. 根据中间结果修改计划；
6. 持续执行，直到形成最终结论、图表、分析结果或实验方案。

论文将其概括为两个主要部分：

* **Biomni-A1：负责推理、规划和行动的 Agent**
* **Biomni-E1：提供工具、软件、数据库和执行环境的科研工作台**

因此可以把 Biomni 理解为：

> **A1 是科研人员的大脑，E1 是实验室、计算机、数据库和工具箱。**

Science 论文将 Biomni 描述为一种通用生物医学 AI Agent，其核心架构结合了大模型推理、检索增强规划和基于代码的执行。([科学杂志][1])

# 一、Biomni 的总体架构

它的完整结构可以分成两个阶段：**离线构建科研环境**和**在线执行科研任务**。

```text
                    Biomni 离线构建阶段
                           
  2,500篇近期生物医学论文，覆盖25个研究方向
                         │
                         ▼
             Action Discovery Agent
       提取论文中的研究任务、软件、数据库和方法
                         │
                         ▼
          生物医学专家和软件工程师人工整理
        去重、封装、编写说明、测试工具是否可用
                         │
                         ▼
                Biomni-E1 科研环境
       ┌──────────┬──────────┬───────────┐
       │150种专用工具│105个软件包 │59个数据库/数据源│
       └──────────┴──────────┴───────────┘


                    Biomni 在线工作阶段

 用户问题、研究目标、数据文件
              │
              ▼
       资源检索器 Retriever
 从E1中选择相关工具、软件、数据库和知识
              │
              ▼
        Biomni-A1 主Agent
        制定分步骤研究计划
              │
              ▼
       生成 Python/R/Bash 代码
              │
              ▼
     在 Biomni-E1 中执行代码和工具
              │
              ▼
         获得中间结果 Observation
              │
        ┌─────┴─────┐
        │结果是否足够？│
        └─────┬─────┘
          否  │  是
        修改计划│
        重新执行│
             ▼
      最终结论、图表、报告或实验方案
```

这个架构最关键的地方是：**Biomni 并不是按照预先写死的工作流运行，而是根据任务动态组合工具、数据库和代码。**

# 二、Biomni-E1：Agent 的生物医学科研环境

## 1. E1 是什么

E1 可以理解为一个经过统一整理的“虚拟生物医学实验室”。

普通大模型即使知道 Scanpy、DESeq2、PLINK 或 AlphaFold 是什么，也不意味着它能够正确安装、调用、组合这些软件。E1 的作用就是把这些分散的软件、数据库、分析函数和专业方法整理成一个 Agent 可以实际使用的环境。

论文中的 E1 包括：

| 资源类型      |  数量 | 作用                |
| --------- | --: | ----------------- |
| 专用生物医学工具  | 150 | 执行具体研究任务          |
| 软件包和命令行程序 | 105 | 完成标准生物信息学和计算生物学分析 |
| 数据库和数据资源  |  59 | 查询基因、疾病、药物、蛋白质等信息 |

这些资源覆盖论文所分析的25个生物医学研究方向。

---

## 2. 150种专用工具

这里的“工具”不只是普通的软件函数，而是经过封装的、能够完成特定科研任务的操作单元。

例如，一个工具可能负责：

* 设计 PCR 引物；
* 分析单细胞 RNA 测序数据；
* 预测药物的 ADMET 性质；
* 进行虚拟药物筛选；
* 分析 RNA velocity；
* 设计分子克隆流程；
* 预测蛋白质或核酸性质；
* 完成特定统计分析；
* 根据实验目标生成实验步骤。

每个工具至少需要具有：

* 明确的工具名称；
* 对功能和适用场景的说明；
* 输入参数和输出格式；
* Agent 可以读取的运行日志；
* 至少一个经过测试的示例；
* 足够专业，不能只是已有基础函数的简单包装。

这些工具最初由 Action Discovery Agent 从论文中发现，然后由生物医学专家和软件工程师人工筛选、实现和测试，而不是完全由大模型自动生成后直接投入使用。

### 工具与软件包的区别

例如：

* **Scanpy** 是一个软件库；
* “对单细胞数据完成质控、标准化、聚类并提取差异基因”可以被封装成一个专用工具。

软件包提供基础能力，专用工具把这些能力组织成更接近科研任务的操作。

---

## 3. 105个科研软件包

E1 将大量生物医学软件放进统一的计算环境中，例如：

* Scanpy；
* DESeq2；
* PLINK；
* Biopython；
* ViennaRNA；
* MACS2；
* 各种序列分析、遗传学、单细胞分析和药物分析软件。

这些软件可能采用完全不同的调用方式：

* Python 库；
* R 软件包；
* Bash 命令；
* 独立命令行程序。

Biomni 将它们放进统一环境，因此 A1 可以在同一个任务中交替使用 Python、R 和命令行程序，而不需要每次重新安装或人工配置。

例如，一次任务可能包含：

```text
Python：读取单细胞 h5ad 文件
   ↓
Scanpy：聚类和差异表达分析
   ↓
R / DESeq2：进行另一种差异分析
   ↓
Python / gseapy：做通路富集
   ↓
数据库查询：验证相关基因和疾病关系
```

这正是 Biomni 能够处理跨工具科研工作流的基础。

---

## 4. 59个数据库和数据资源

Biomni 把数据库分成两类。

### 第一类：具有 API 的在线数据库

例如：

* PDB；
* Open Targets；
* ClinVar；
* 其他基因、蛋白质、疾病和药物数据库。

对于这类数据库，Biomni 提供统一的查询接口。A1 可以先用自然语言表达查询意图，系统内部再根据数据库的 schema 生成相应查询并执行。

例如，A1 可能提出：

> 查询 BRCA1 的致病性变异，以及这些变异对应的疾病证据。

系统需要把这句话转成 ClinVar 或其他数据库能够接受的查询格式，再将查询结果返回给 A1。

### 第二类：没有方便 API 的本地数据

这类数据库会预先下载、清洗，并放入本地 data lake。很多数据被整理成 Pandas DataFrame，使 Agent 可以直接编写 Python 代码进行筛选、合并和统计。

因此，E1 不只是一个“搜索引擎”，也包含可以直接计算的结构化数据。

---

## 5. 文献检索能力

E1 还包含 PubMed、Google Scholar 等文献检索工具。

但文献检索不是为了简单复制论文摘要，而是可以嵌入研究流程，例如：

1. 计算得到候选基因；
2. 检索这些基因与某种疾病是否已有联系；
3. 查找相关机制论文；
4. 对计算结果进行交叉验证；
5. 在最终报告中给出证据来源。

所以文献检索只是 Biomni 的一种行动，而不是 Biomni 的全部。

---

# 三、Biomni-A1：负责思考和执行的主 Agent

A1 是整个系统的核心。它可以进一步拆成六个功能模块。

---

## 1. 主推理模型

A1 内部有一个主大语言模型，负责：

* 理解用户问题；
* 将研究问题拆成子问题；
* 决定分析顺序；
* 生成代码；
* 阅读运行结果；
* 判断当前证据是否足够；
* 修改后续步骤；
* 汇总最终答案。

因此，底层大模型本身只是 A1 的“推理引擎”。真正让它成为 Agent 的，是外围的规划、工具检索、代码执行和反馈循环。

---

## 2. Resource Retriever：资源检索器

E1 中有数百种资源，不可能把每个工具、软件和数据库的完整说明都放入主模型的上下文。

因此，在主 Agent 开始规划前，会先运行一个资源检索器。

输入可能是：

> 分析患者肿瘤单细胞数据，寻找与免疫逃逸相关的细胞群和通路。

资源检索器会从完整资源库中选出可能相关的项目，例如：

```text
工具：
- 单细胞数据质控工具
- 差异表达工具
- 细胞类型注释工具
- 通路富集工具

软件：
- Scanpy
- gseapy

数据库：
- MSigDB
- CellMarker
- Open Targets

知识：
- 单细胞肿瘤免疫分析流程
```

然后只把这些相关资源的说明交给主 Agent。

这样做有两个重要作用：

* 减少上下文长度；
* 避免大模型在大量无关工具中随意选择。

论文的消融实验也显示，资源检索器能够明显压缩上下文，并改善任务表现。

### 这里不是普通的文档 RAG

普通 RAG 通常是：

```text
问题 → 检索几段文字 → 根据文字生成答案
```

Biomni 的检索更像：

```text
研究目标
  → 检索能够执行任务的工具、数据库和软件
  → 规划如何使用这些资源
  → 真正运行它们
```

所以更准确的名称是：

> **Retrieval-Augmented Planning，检索增强规划。**

检索到的不是只有知识文本，而是可执行的科研能力。

---

## 3. Planner：研究计划生成器

获得相关资源后，A1 会生成一个编号的研究计划或 checklist。

例如：

```text
1. 读取并检查用户上传的单细胞数据
2. 完成细胞和基因质量控制
3. 标准化数据并进行降维、聚类
4. 识别不同细胞群的差异表达基因
5. 获取癌症相关通路基因集
6. 对差异基因做通路富集分析
7. 查询文献和数据库验证主要发现
8. 汇总结果并生成图表
```

这个计划不是固定模板。

执行过程中，A1 会持续更新：

* 哪些步骤已经完成；
* 哪些步骤失败；
* 哪些结果需要进一步验证；
* 是否需要加入新的分析；
* 是否需要更换方法。

论文给出的系统提示明确要求 Agent 维护编号计划，并标记步骤的完成或失败状态。

---

## 4. CodeAct：以代码作为行动

这是 Biomni 架构中最重要的设计之一。

很多 Agent 使用普通的 function calling：

```text
调用工具A
等待结果
调用工具B
等待结果
调用工具C
```

Biomni 采用的是类似 **CodeAct** 的思路：让大模型直接生成代码，把代码当作一种通用行动语言。

例如，它可以生成：

```python
import scanpy as sc
import gseapy as gp

adata = sc.read_h5ad("adata.h5ad")

sc.pp.filter_cells(adata, min_genes=200)
sc.pp.normalize_total(adata)
sc.pp.log1p(adata)
sc.tl.rank_genes_groups(adata, groupby="cell_type")

genes = (
    adata.uns["rank_genes_groups"]["names"]["Tumor"]
    .tolist()[:200]
)

enrichment = gp.enrichr(
    gene_list=genes,
    gene_sets="MSigDB_Oncogenic_Signatures"
)
```

代码作为行动有几个明显优势。

### 可以一次组合多个工具

它不必每次只调用一个函数，而是可以写出完整的分析流程。

### 可以表达条件逻辑

```python
if data_quality < threshold:
    perform_additional_filtering()
else:
    continue_analysis()
```

### 可以使用循环

```python
for cell_type in cell_types:
    run_differential_expression(cell_type)
```

### 可以进行并行处理

例如同时分析多个基因集、多个样本或多个候选药物。

### 可以直接操作原始数据

Agent 不只是调用预定义工具，还能够：

* 读取 CSV、H5AD、FASTA 等文件；
* 清洗数据；
* 合并表格；
* 编写新的分析函数；
* 绘制图表；
* 保存中间结果。

因此，代码成为连接软件、数据库、工具和用户数据的“通用胶水”。

---

## 5. Execution Engine：代码执行器

A1 生成代码之后，代码不会停留在文本中，而是会在 E1 环境里真正执行。

支持的主要形式包括：

* Python；
* R；
* Bash；
* 命令行生物信息学软件。

执行器会把运行结果返回给 Agent，包括：

* 标准输出；
* 错误日志；
* 统计结果；
* 数据表；
* 图像文件；
* 软件运行状态；
* 数据库查询结果。

这一步是 Biomni 与普通聊天模型最明显的区别。

普通模型可能“描述如何分析”；Biomni 会真正执行分析。

---

## 6. Observation–Reasoning 循环

代码执行后，A1 会观察结果。

例如第一次分析可能得到：

```text
发现 3 个显著富集通路：
- MYC targets
- KRAS signaling
- Hypoxia

但其中一个细胞群只有 17 个细胞，结果可能不稳定。
```

A1 可能据此修改计划：

```text
原计划：
直接解释该细胞群的通路富集结果。

修改后：
1. 检查该细胞群是否为低质量细胞；
2. 使用重采样评估差异基因稳定性；
3. 与相邻细胞群合并后重新分析；
4. 再决定是否报告该结果。
```

于是形成循环：

```text
思考
  ↓
制定或修改计划
  ↓
生成代码
  ↓
执行
  ↓
观察结果
  ↓
再次思考
```

直到 A1 判断已有足够证据，才输出最终答案。论文将这一过程描述为：计划、代码执行和观察结果交错进行，并通过中间结果不断调整后续步骤。

---

# 四、Biomni 一次任务是怎样运行的

论文图中给出了一个类似任务：

> 用户提供一个 `adata.h5ad` 单细胞数据文件，询问差异表达基因中是否富集了致癌通路。

完整流程大致如下。

## 第一步：理解研究目标

A1 首先识别：

* 数据类型是单细胞转录组；
* 输入文件是 AnnData/H5AD；
* 需要进行差异表达；
* 需要获得致癌通路基因集；
* 需要做基因集富集；
* 最好进一步用文献或数据库验证。

---

## 第二步：检索资源

Retriever 可能选择：

* Scanpy；
* 差异表达工具；
* 通路富集工具；
* MSigDB 致癌基因集；
* 文献查询工具；
* 相关数据库。

无关工具，例如蛋白质结构预测或引物设计，不会被塞进主模型的上下文。

---

## 第三步：生成计划

A1 制定计划：

1. 读取 H5AD；
2. 检查数据结构；
3. 确定分组变量；
4. 计算差异表达基因；
5. 获取致癌通路；
6. 运行富集分析；
7. 检查显著性和多重检验；
8. 结合数据库和文献解释结果。

---

## 第四步：生成并运行代码

A1 编写 Python 代码，调用 Scanpy 和富集分析软件。

E1 执行代码，返回：

* 差异基因列表；
* 富集通路；
* P 值和校正后的 P 值；
* 富集分数；
* 图表；
* 错误或警告信息。

---

## 第五步：检查中间结果

A1 可能发现：

* 分组列名称判断错误；
* 某些组样本量过少；
* 没有进行批次校正；
* 使用的背景基因集不合适；
* 富集结果不够稳定。

此时它会修改代码或补充步骤，而不是直接编造答案。

---

## 第六步：补充验证

A1 可以进一步：

* 更换差异分析方法；
* 检查不同阈值下结果是否一致；
* 查询通路数据库；
* 检索代表性论文；
* 比较多个细胞群；
* 对候选基因进行交叉验证。

---

## 第七步：生成最终报告

最终输出可能包括：

* 哪些致癌通路显著富集；
* 哪些基因驱动了富集结果；
* 统计显著性；
* 生物学解释；
* 结果的不确定性；
* 后续实验建议；
* 分析代码和图表。

论文 Figure 1 展示的核心流程正是“检索资源—制定结构化计划—生成可执行代码—观察结果—迭代执行—形成结论”。

---

# 五、它是单 Agent 还是多 Agent？

严格来说，Biomni 更接近：

> **一个主 Agent 加若干辅助模型和执行模块。**

在线运行时最重要的是：

* **A1 主 Agent**：总体推理、规划和决策；
* **资源检索 LLM**：从 E1 中选择相关资源；
* **执行环境**：运行代码和软件；
* **数据库查询内部模型**：必要时将自然语言转成数据库查询。

因此，它不是典型的“多个专家 Agent 开会”式多 Agent 系统。

论文中还提到一个 **Action Discovery Agent**，但这个 Agent 主要用于系统建设阶段：阅读大量论文，发现应该在 E1 中加入哪些科研任务、工具和数据库。它并不是每次用户提出问题时都参与运行。

可以这样区分：

| 模块                     | 何时运行    | 作用              |
| ---------------------- | ------- | --------------- |
| Action Discovery Agent | E1建设阶段  | 从论文中发现科研操作      |
| Resource Retriever     | 每次任务开始时 | 选择相关资源          |
| Biomni-A1              | 整个任务过程中 | 规划、执行、观察和重规划    |
| E1执行环境                 | 执行阶段    | 真正运行代码、软件和数据库查询 |

从论文架构来看，Biomni 并没有把一个独立的“批评 Agent”或“验证 Agent”设为必需核心组件。验证主要来自代码执行结果、统计检查、数据库或文献回查，以及 A1 对计划的迭代修正。这一点与某些 planner–executor–critic 多 Agent 系统不同。
