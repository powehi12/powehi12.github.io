# 前言
**标题**：ClinEnv: An Interactive Multi-Stage Long Horizon EHR Environment for Agents
**作者单位**：Georgia Institute of Technology、北京大学、UT Southwestern Medical Center、清华大学（Yuxing Lu, Yushuhong Lin, Wenqi Shi, J. Ben Tamo, Xukai Zhao, Jinzhuo Wang, May Dongmei Wang）
**论文**：https://arxiv.org/abs/2606.02568 （arXiv:2606.02568v1，2026-06-01）
**代码**：https://github.com/ylin766/ClinEnv ｜ **数据**：https://huggingface.co/datasets/ylin766gatech/ClinEnv（需先通过 PhysioNet 合规审核）｜ **Demo**：https://clinenv-demo.vercel.app/
**标签**：EHR 智能体；临床决策 Benchmark；长程序贯决策；交互式评测环境

**摘要**：一句话核心思想——**别再让模型做选择题了，把它扔进真实住院病历里当主治医生，让它自己开口问信息、一步步下不可撤回的医嘱，然后看它能不能还原这个病人真实的诊疗过程**。具体来说，ClinEnv 从 MIMIC-IV 真实住院记录出发，用一条全自动流水线把每次住院切成有先后顺序的"决策阶段"，每个阶段模型开局什么都看不到，必须主动去问病人、护士、化验、既往史四个专门 agent，问够了再提交用药、操作、诊断三类决定；打分同时看"决定对不对"（用 ATC 药物本体和 ICD 层级 F1 做确定性匹配）和"信息是怎么问出来的"（覆盖率、查询效率、化验浪费率、药费）。作者把这套范式命名为 Longitudinal Inpatient Simulation（LIS）。结果七个模型里最强的只拿到 0.31 决策 F1，而且"结果好"和"过程好"几乎不相关，诊断能还原（0.51）但管理动作几乎不会做（0.17）。

# Step 1：论文解读

## 1：为什么现有的医疗 Benchmark 都不太够
大模型在 USMLE 这类医学执照考试上已经能追平甚至超过专家，但作者一句话戳破：真实住院压根不是从 A/B/C/D 里挑一个。真实的主治医生每天面对的是这三件事：**信息是残缺的、要自己去要**（没人主动把化验单塞你手里）；**决定是有先后、且不可撤回的**（今天上了万古霉素，明天不能假装没上过）；**决定是多模态的**（同时要管药、操作、诊断三条线）。
### 1.1：三类现有工作各自"缺一块"
作者把已有工作分成三家，每家都有一处结构性妥协：一是**数据交互类**（EHRSQL、MIMIC-SQL、FHIR-AgentBench、MedAgentBench），把病历当成一个可查询的数据库，考的是"你会不会写 SQL / 调 API"，而不是"你知不知道该查什么、查到了该干嘛"；二是**问诊对话类**（AgentClinic、MedDialBench、MAQuE、HELPMed、AMIE），确实是交互的，但病人是 LLM 演的，标准答案的上限就被"喂给模拟器的那份考题短案例"锁死了，而且中间过程只能靠 LLM-as-judge 打分；三是**代码执行类**（MedAgentGym、MedCalc-Env），把临床推理降维成"写对一段代码或一个公式"。
### 1.2：一个很好用的类比
论文反复拿**编程 agent** 做类比，这个类比是本文叙事的骨架：HumanEval 那种静态函数测试 → SWE-bench 那种可执行的真实仓库环境，评测基建的升级直接把整个领域往前推了一大截，而且环境本身还能当训练信号用。医疗评测现在正卡在"从 HumanEval 往 SWE-bench 走"的这一步上。
> 🔪 **锐评**：这个类比是本文最好卖的地方，但也是最需要警惕的地方。SWE-bench 之所以成立，是因为"单元测试通过"是**客观且唯一**的成功判据。而"这个病人该用哪个药"根本没有唯一解。后面 Step 3 我会展开——这不是细节问题，是这篇论文整个分数体系能不能被解读的根子问题。

## 2：LIS 范式——它到底"新"在哪五个维度
作者定义的 Longitudinal Inpatient Simulation 由五个维度共同构成：真实 EHR 纵向轨迹、多阶段序贯决策、跨异构源的主动信息获取、基于医学本体的确定性打分、以及成本感知的过程指标。作者做了一张对比表逐个打勾，宣称 ClinEnv 是第一个五项全占的工作。
说人话就是：**别的 benchmark 每次只满足其中三四项，ClinEnv 想一次性全要**。
> 🔪 **锐评**：这种"我做一张表，把五个维度列出来，然后只有我这一行全是 ✓"的写法，在 benchmark 论文里是标准操作，也是 OpenReview 上审稿人最爱开火的地方——因为**维度是作者自己定的**。你完全可以反过来定一套维度（比如"是否有医生基线""是否支持多正确答案""标注是否人工校验过"），那 ClinEnv 这一行就会出现 ✗。这张表的说服力取决于你信不信这五个维度是"临床评测该有的样子"，而不是"我做出来的样子"。

## 3：数据是怎么来的——把住院记录拍平成一条时间线
底座是 MIMIC-IV v3.1 + MIMIC-IV-Note v2.2。对每一次住院（按 subject_id 和 hadm_id 关联），把结构化表和临床文本合并成一条"住院级时间线"：结构化侧包括入院记录、化验和微生物结果、医嘱与给药记录、ICU 监测事件、出入量、操作事件、ICD 编码的诊断与操作；文本侧是出院小结和影像报告。每一行都变成一个带出处的事件，携带统一的 event_time 和 source_table，然后按时间排序。
**打个比方**：原来病历是散在十几个抽屉里的一堆纸（化验单一叠、医嘱一叠、护理记录一叠），现在全部按时间戳串成了一条微博时间线，每条都标注了"这条来自哪个抽屉"。文本负责给决策抽取和既往史查询提供叙事上下文，结构化记录负责提供带时间戳的客观观测和可用于评测的编码金标准。

## 4：全自动造题流水线——不用人工标注是怎么做到的
这是全文工程量最大、也最值得复现者细看的部分。整条流水线用 Claude-Sonnet-4.6 当规划骨干。
### 4.1：Phase A 决策抽取
让规划器读出院小结，把这次住院里主治医生做过的每一个决定抽出来，并标上类型（用药 / 操作 / 计划）。如果拿不到完整的出院小结自由文本，就退化成拼接四个章节：主诉、现病史、住院经过、出院诊断。
### 4.2：Phase B 时间锚定（把"做过什么"钉到"什么时候做的"）
出院小结只说"住院期间予以抗感染治疗"，但不说是第几天。于是作者用一个**顺序向前滑动窗口**的 agent：给它一个窗口内的事件序列，配 mark_single / mark_range 两个工具，让它标出这个决策对应哪个（或哪段）事件。标中了就把指针推到该位置，下一个决策从这之后接着找；没标中就整体前移一窗重试；找到时间线尽头还没匹配上就放弃这个决策。只锚定在入院前事件上的决策直接丢弃。
**关键设计是"单调向前"**——因为出院小结的叙述顺序基本等于时间顺序，指针只进不退，既省算力又天然保证了阶段之间不会时间倒错。
### 4.3：Phase C 阶段切分
第 k 个阶段能看到的上下文，是"上一阶段用掉的最后一个事件之后" 到 "本次决策锚点之前"的那一段。两种情况会跳过：一是根本没有上下文窗口（上一阶段已经吃到了这里）；二是这条用药决策对应的药在当前窗口里已经在用了（避免把"继续用药"当成"新决定"）。另外，每个 case 末尾都会强行追加一个"最终诊断阶段"，它的上下文是从最后一个决策一直到出院。
### 4.4：Phase D 诊断可溯性扫描
出院时的 ICD 码不是每一个都在住院过程里真的被处理过（有些是陈旧合并症，顺手编上去的）。所以作者用带重叠的滑窗（窗口 W、步长 S<W）扫一遍时间线，只有被至少一个窗口确认"确有证据或确有处理"的 ICD 码，才进入最终诊断阶段的金标准。这一步很实在——**不做的话，模型会被要求猜出一堆病历里根本没体现的编码**。
### 4.5：Phase E 分类与确定性富化
先用 LLM 把每个阶段的原始决策描述归类成四种之一（用药 / 操作 / 诊断 / 计划）；用药还要再判定动作类型：start / stop / switch / adjust，其中 adjust 可以带方向（增量 / 减量）。然后是关键的一句——**金标准字段的填充是零 LLM 调用的**：药名直接从处方、药房、eMAR 表里读；操作和诊断的 ICD 码直接取自对应的编码事件。
> 🔪 **锐评**：这个"分类靠 LLM、取值靠数据库"的分工是聪明的，它把 LLM 的错误限制在"标签打歪"而不是"编造了一个不存在的药"。但要注意，**Phase A 和 Phase B 仍然完全是 LLM 的活儿**，而这两步决定了"有哪些题"和"每道题该在什么时刻问"——流水线最上游的误差会一路传到底，正文里没给这两步的准确率数字（只说附录 D.2 有构建质量检查）。另外一个小瑕疵：正文写的是 "four-phase pipeline"，却实打实列了 A 到 E 五个阶段，Figure 1 的说明里又写成 five-step。**同一页里自相矛盾**，这种细节在顶会 rebuttal 阶段会被逮到。

## 5：交互环境——四个"只能看自己那一块"的信息 agent
环境用四个专门 agent 暴露临床信息，每个都由 GPT-5.4-mini 驱动，并且被限制在一个专属的 readview（EHR 事件的一个过滤投影）里：**病人 agent** 拿人口学、主诉、现病史、既往史，用大白话像真病人一样回答主观感受；**护士 agent** 拿生命体征、出入量、给药记录，报床旁客观观察；**化验 agent** 拿化验和微生物结果，用语义匹配去解析自然语言的检验名，没这项记录就什么都不返回；**既往史 agent** 在有过既往住院时提供之前的出院小结。
**这个"readview 隔离"是环境设计的精髓**：护士 agent 哪怕内部知道化验结果，它的视野里也根本没有这些字段，所以不可能漏答案给你。平均每个阶段有 3.67 个 agent 可用，每个 readview 里平均藏着 32.8 条关键临床事实。

## 6：两种模式，以及一个很有争议的"提交接口"
### 6.1：Direct 模式 vs Interactive 模式
Direct 模式下，模型一上来就拿到该阶段的全部观测（静态患者背景 + 到本阶段结束为止的累积事件序列），不用问直接交答案——这是消融用的对照组。Interactive 模式才是主菜：模型开局零临床数据，每一轮只允许调用一个工具，观测靠一问一答累积；直到它调用 finalize_decision，或者到达 60 轮上限。可用工具是 ask_patient、ask_nurse、order_lab、get_history_summary、get_history_detail 五个查询工具，加 submit_medication / submit_diagnosis / submit_procedure / submit_plan / finalize_decision 五个提交工具。
### 6.2：结构化提交接口——"我告诉你要交几个"
这是全文最值得单独拿出来说的设计。为了把临床推理质量和输出格式的干扰解耦，提交接口做了两重约束：第一，**只暴露本阶段金标准里真实存在的那几类提交工具**，不存在的类型直接不给（比如这个阶段没有操作决策，就压根没有 submit_procedure 这个按钮）；第二，**直接告诉模型每一类要交几个**。因为提交数量和金标准数量强制相等，每类内部的匈牙利匹配就在等大的两个集合上进行，precision 和 recall 的差异只来自匹配质量而非数量错配。
> 🔪 **锐评**：作者的辩护是"这样测的才是临床决策准确率，而不是模型猜格式的能力"，逻辑上说得通。但代价极其昂贵：**"知道现在要不要动手、要动几手"本身就是临床能力的核心组成部分**。真实的主治医生没人会告诉他"你今天该开 2 个药 1 个操作"。这个接口等于把"决策的触发与规模判断"这个最难的部分免费送给了模型，然后声称测的是"attending physician 的能力"。更微妙的是，它还泄露了信息：告诉模型"这个阶段有 submit_procedure"，等价于告诉它"这里该做个操作了"。所以 0.31 这个数字是一个**被大幅放水后的上界**，真实的端到端能力只会更低——从这个角度说，作者的悲观结论其实是被低估了，这反而对论文有利。

## 7：怎么打分——"确定性"这个卖点有多硬
### 7.1：决策准确率（结果侧）
在诊断、用药、操作三个类型组内部**分别**用匈牙利算法做最大化总匹配分的指派，再拼接成阶段级指派；阶段 F1 是从匹配分导出的连续 precision 与 recall 的调和平均。
**用药打分**：动作类型是**硬门**——start/stop/switch/adjust 只要和匹配到的金标准不一致，不管药名多像都直接判 0，这会驱使匈牙利算法优先选择动作一致的配对。动作对上之后，药名相似度走 ATC 层级部分给分：完全同名直接 1.0；否则通过 RxNorm API 把两个药名都解析成 ATC 码，按最长公共前缀长度给分——化学亚组（5 位）0.8、药理学类（4 位）0.6、治疗学组（3 位）0.3、解剖学组（1 位）0.1，其余 0。对 adjust 决策，如果双方都明确指定了方向且相反，最终得分再乘 0.5；只要有一方没指定方向就不罚。
**这个 ATC 阶梯很符合临床直觉**：你把头孢曲松写成了头孢他啶（同为三代头孢），比你写成布洛芬要有价值得多，不该同样是 0 分。
**诊断和操作打分**：模型交的是自由文本，金标准是 ICD 码，所以先两步映射：在覆盖 ICD-9-CM / ICD-10-CM / ICD-9-PCS / ICD-10-PCS 全表的 embedding 索引上按余弦相似度取 top-15，再用一个 LLM reranker 选最佳。然后把预测码和金标准码各自展开成 ICD 层级里的完整祖先集合，在两个集合上算 Hierarchical F1（HDF1）。
### 7.2：过程质量（信息采集侧）
**覆盖率**：对每个被激活的 agent 角色，把完整 readview 和该 agent 本阶段的所有回答一起交给一个 judge，让它枚举 readview 里的关键临床事实，逐条标记"这条有没有在对话里出现过"，得到该角色的覆盖率；阶段覆盖率是各激活角色的宏平均。**效率**：光看覆盖率不惩罚滥问，所以再除以"平均每个信息源被问了几次"——设 K 为本阶段的信息查询次数，激活 agent 数为 |A|，效率 = 覆盖率 / max(1, K/|A|)。当 K ≤ |A| 时不罚，超过之后按冗余程度成比例压低。作者的理念是：**一个高效的问诊，应该用大约一句话就把一个信息源榨干**。
**化验浪费率**：每个模型点的化验，通过同样的"embedding 检索 + LLM 重排"两步流程映射到 CMS 临床实验室收费表的报销价；凡是超出金标准临床画面所支持的化验，一律算不必要开销，浪费率 = 多余化验费用之和 / 所点化验费用之和。**药费**：药名 → RxNorm CUI → NDC 码 → NADAC 数据库单价 p；同时 RxNorm CUI → ATC 码 → WHO 限定日剂量 DDD，单药日费用 c = p × DDD，阶段级指标是所有合格提交的日费用总和。
> 🔪 **锐评**：注意看这里的**内在张力**。论文在 Related Work 里明确批评 AgentClinic 那一家"中间行为只能靠 LLM-as-judge 打分"，把"确定性打分"立成自己的核心卖点。但你数一数：诊断/操作打分要靠 **LLM reranker** 选 ICD 码，覆盖率要靠 **LLM judge** 枚举并核对事实，化验费和药费映射也各要一次 **LLM 重排**。真正 100% 确定性的，其实只有"用药动作门 + ATC 前缀比对"这一小块。所以准确的说法是"**比对手更确定性**"，而不是"确定性的"。这个措辞在 rebuttal 里是会被要求改的。另外，把"金标准里没有的化验"一律定义成浪费，等于假设**真实医生点的化验集合是最优的**——现实中医生漏点、乱点都很常见，这个指标本质上测的是"模仿这家医院的开单习惯"，不是"临床上是否必要"。

# Step 2：实验部分

## 1：这个 Benchmark 长什么样
从 1,809 名患者中采样了 3,509 次住院（只保留至少能产出一个有效决策阶段的），并按时间跨度做了分层，保证长短住院都有充分代表。最终得到 9,297 个决策阶段、26,043 条金标准决策，平均每个 case 2.65 个阶段、每个阶段 2.80 条决策。
Case 长度分布：单阶段 718 个（20.5%）、双阶段 1,043 个（29.7%）、长程（≥3 阶段）1,748 个（49.8%）。决策类型分布严重不均：诊断 18,664 条（71.7%）、用药 5,571 条（21.4%）、操作 1,808 条（6.9%）。用药动作里 start 占 79.1%、stop 7.5%、adjust 9.5%、switch 3.8%。因为来自真实住院而非人工题库，覆盖面很宽：2,128 个不同 ICD 码、488 种不同药物。
> 🔪 **锐评**：**71.7% 是诊断**这件事值得警惕。诊断恰恰是模型最擅长的那一类（Dx 0.51），而全文的核心叙事是"管理决策才是硬骨头"。好在总 F1 用的是 stage-macro 平均而非按决策数加权，一定程度上稀释了这个失衡；但也意味着 0.306 这个总分的构成需要小心解读——它不是"71.7% 的题拿了 0.51 分"那种加权结果。另外 switch 只占 3.8%（约 210 条），而 switch 是临床上最考验推理的动作（"为什么要换药"），**样本量小到几乎无法单独做统计**。

## 2：总体结果——最强的模型也只有 0.31
测了七个模型：GPT-5.4 / mini / nano、Llama-3.1-70B / 8B、Gemma-3-27B / 12B（专有模型是在 PhysioNet 要求的零数据留存策略下访问的）。GPT-5.4 在所有结果指标上领先：决策 F1 0.306、诊断 0.511、操作 0.379、信息覆盖率 0.430。但这离"刷爆"差得很远。
其余模型的总 F1 挤在一个很窄的带里：GPT-5.4-mini 0.258、GPT-5.4-nano 0.254、Gemma-3-27B 0.228、Llama-3.1-70B 0.226、Llama-3.1-8B 0.202、Gemma-3-12B 0.197。
> 🔪 **锐评**：**8B 拿 0.202，最强模型拿 0.306**——这个差距小得让人不安。一个健康的 benchmark 应该能把 8B 和旗舰模型拉开代差。这里只有 1.5 倍，说明分数里有相当大一块来自"任务本身的天花板"（等效方案被判 0 分、ICD 映射误差等），而不是模型能力差异。作为**训练信号**（作者暗示的 SWE-bench 式用法）这是个隐患：信噪比太低，RL 很难从中学到东西。

## 3：结果好 ≠ 过程好，这是全文最有价值的观察
Llama-3.1-70B 拿到了全场最高的用药分（0.101），但同时是覆盖率最低（0.140）、轮数最多（14.1）、化验浪费最高（35.8%）的那个。GPT-5.4-nano 是它的镜像：准确率有竞争力，轮数最少（4.4），浪费最低（4.1%）；它用一半的查询量就摸到了 GPT-5.4 大部分的覆盖率，成为信息效率最高的模型（0.281 对 0.274），尽管 GPT-5.4 绝对采集量更大。
**说人话**：有的模型像个话痨实习医生，问了一堆废话、开了一堆没用的化验，最后蒙对了药；有的模型三两句问到点子上。**只看最终答案，你完全分不出这两种**——而在真实医院里，这两种医生的成本和风险差着数量级。
> 🔪 **锐评**：观察本身很有价值，但**证据强度撑不住这个叙事**。所谓"最高用药分"是 0.101 对 GPT-5.4 的 0.097——**差 0.004**，论文没给置信区间。用一个几乎必然落在噪声里的差距去讲"最强用药能力却最差过程"的反差故事，是典型的 cherry-pick。把这个例子换成"Llama-3.1-70B 用药分与最强模型持平，但浪费率高 3.5 倍"，结论不变而且站得住脚——作者选了更戏剧化但更脆的那个说法。

## 4：越往后越不会——长程退化是真的
所有模型在 ≥3 阶段的子集上都比全集更差，GPT-5.4 从 0.306 掉到 0.235。
更细的分析只看**管理阶段**（带用药或操作决策的），把每个 case 末尾那个分数虚高的诊断阶段剔除掉，否则会掩盖管理决策的真实轨迹。结果：决策 F1 随阶段序号单调下降，GPT-5.4 从第一个管理阶段的 0.21 掉到第四个阶段的 0.03 以下，其余模型全部收敛到接近零。
**最关键的一句在这里**：瓶颈不是信息获取。覆盖率对 GPT-5.4 基本持平，对弱模型甚至随病历变长而上升，但决策照样劣化。真正崩掉的是效率——GPT-5.4 的每阶段查询次数从约 4 次飙到 50 次以上，而覆盖率还是停在 0.45 附近。也就是说，后期阶段被大量"问不出新东西"的冗余查询占满，决策反而更差。真正的约束是后期的临床推理，不是信息可得性。
**打个比方**：这个模型不是"看不到化验单"，而是"化验单摊了一桌子，它反复重看同一张，却不知道该怎么把今天的血象和三天前用的抗生素联系起来"。**这是记忆整合 / 状态维护的失败，不是检索的失败**——对你做 long-horizon agent 来说，这一条比全文任何一个数字都重要。
> 🔪 **锐评**：Table 5 里有个和叙事对不上的数：GPT-5.4 在长程子集上的化验浪费率是 **2.3%**，反而**低于**全集的 10.4%。如果长程真的是"被冗余查询淹没"，浪费率不该降。合理解释可能是分母（总化验开销）在长程里涨得更快，稀释了比率——但论文一个字没提这个反常。审稿人会问。

## 5：问得越准，浪费越少（而不是问得越多）
如果"采集信息"只是"多问几句"，那覆盖率越高就该买来越多的无用化验。Figure 3 显示的恰恰相反：覆盖率和化验浪费呈负相关，采集到更多相关信息的模型，浪费也更少，GPT-5.4 落在最有利的那个角。
这条结论很干净：**"会问"和"瞎问"是两种能力，而不是同一条轴的两端**。它顺带为过程指标的存在合法性做了辩护——如果覆盖率只是查询次数的代理变量，那这个指标就没必要单独存在了。

## 6：诊断能还原，管理学不会
这是全文最锋利的对比：模型还原出院诊断远比还原管理动作可靠，0.51 对 0.17 F1。拆开看用药分尤其惨烈——七个模型的 Rx 分全部落在 0.070 到 0.101 之间，也就是说**在开药这件事上，旗舰模型和 12B 小模型没有实质区别，且都接近地板**。
**为什么会这样？** 直觉上讲得通：诊断在某种意义上是**回溯性**的——所有证据都摆在时间线里，模型只要做一次模式识别（"发热+白细胞高+胸片浸润影 = 肺炎"），这正是它在 MedQA 上练了千百遍的技能。而管理是**前瞻性**的——"现在该上哪个抗生素"取决于本院药敏谱、患者肾功能、既往过敏史、成本、以及一堆没写在病历里的科室惯例。**前者是识别，后者是选择**，而模型只学会了前者。
> 🔪 **锐评**：这是本文最有说服力、也最应该被后续工作接着做的发现。但要诚实地说，0.17 这个数字里有多少是"模型不会"、多少是"等效方案被判 0 分"，论文**没有做任何拆解**。哪怕只做一个小规模人工复核（抽 100 个被判 0 的用药提交，让临床医生标注"这个方案在临床上是否也可接受"），整篇论文的可信度会完全不同。这正是我下面那条意见的核心。

# Step 3：other

## 1：重点
**最有价值的是"过程/结果解耦"这个测量维度本身，而不是 0.31 这个分数。** 具体三点：**第一，长程失败的根因被定位到了推理而非检索**——覆盖率基本不掉、查询次数暴涨到 50 次以上、决策 F1 却单调塌到 0.03，这个三联证据清晰地指向"模型无法把新观测和自己此前的行为整合成连贯的病程状态"。对任何做 long-horizon agent 的人来说，这意味着**优化方向应该是状态压缩 / 决策记忆，而不是继续堆检索能力**。**第二，"诊断 0.51 vs 管理 0.17"揭示了一个被 MedQA 类评测系统性掩盖的能力断层**：识别能力已经到位，选择能力几乎为零，而后者才是临床落地的必要条件。**第三，工程上最可复用的资产是那条零人工标注的造题流水线**——"LLM 负责定位和分类、数据库负责填值"的分工，加上"顺序单调滑窗锚定"和"诊断可溯性扫描"两个小设计，是可以直接搬到其他 EHR 数据集（乃至中文病历）上的。坦白说，**这条流水线的可迁移价值高于 ClinEnv 这个数据集本身**。

## 2：意见
**整篇论文的分数体系建立在"MIMIC-IV 里这家医院实际做了什么 = 唯一正确答案"这个未经辩护的假设上，而缺少人类医生基线让这个假设无法被检验——因此 0.31 这个核心数字在字面上不可解释。** 临床决策存在大量等效路径：换一个同类抗生素、把 CT 推迟到明天早上、选择观察等待，都可能同样正确甚至更优，但在 ClinEnv 里全部得 0 分（ATC 部分给分只能缓解同类药的情况，完全救不了"不同但同样合理的治疗策略"）。这直接导致论文的核心论断——"outcome-only benchmark 大幅高估了临床准备度"——**在逻辑上不成立**：0.31 究竟是"模型只有 31% 的临床能力"，还是"模型只有 31% 的概率复现这家医院这一次的具体行为"，作者提供的证据完全无法区分这两者。补救方案其实很便宜：**让若干名主治医生在完全相同的 interactive 环境里盲测同一批阶段**。如果医生自己也只拿到 0.4，那读者立刻就知道这个 benchmark 的天花板在哪、0.31 意味着什么；如果医生拿到 0.85，作者的论断就被强力坐实。没有这条基线，所有绝对分数都只是内部可比的相对排名，却被当成对"临床准备度"的绝对判决来用——这是我作为审稿人会要求在 rebuttal 阶段补上、否则倾向拒稿的一点。

## 3：相关工作
**MedAgentBench（Jiang et al., 2025）** 是"把 EHR 当可查询系统"这一路的代表作，构建了一个虚拟 EHR 环境，配上 100 份患者档案和由医生撰写的交互式任务，考察 agent 在真实医疗数据接口（FHIR 风格）上执行明确定义操作的能力。ClinEnv 对它的批评是：任务是原子的、且由外部预先定义好的，所以测的是数据访问技能，而不是"判断哪些数据重要、这些数据该导向什么行动"的临床推理。它和 ClinEnv 恰好构成互补——**前者测手，后者测脑**。

**MedAgentGym（Xu et al., 2025）** 走的是"编程 agent 类比"的另一条支路，是一个面向生物医学数据科学的、以代码为中心的可扩展 agentic **训练**环境（注意是 training environment 而非纯 benchmark）。ClinEnv 承认自己和它精神相通，但强调差别在于：MedAgentGym 要模型产出的是代码或公式，而 ClinEnv 直指临床决策本身（该开哪个药、该定哪个诊断），并用医生真正在用的医学本体来验证。如果你关心"环境能不能当训练信号用"，这篇是必读的对照。

**MedDialBench（Luo et al., 2026）** 属于问诊对话这一家的最新成员，在 AgentClinic 奠定的"医生 agent × LLM 扮演病人"范式上，加入了参数化的对抗性病人行为（病人会隐瞒、误报、情绪化），专门测诊断鲁棒性。同一家族还有 MAQuE（问诊能力评估）、HELPMed（发现临床知识并不能自动转化为有效的人际互动）和 AMIE（引入真人参与者）。ClinEnv 对整个这一族的核心批评是双重的：金标准的上限被"喂给模拟器的那份考题短案例"锁死，且中间行为只能靠 LLM-as-judge 在自由文本上打分。不过如我在 Step 1 里指出的，**ClinEnv 自己的覆盖率指标同样是 LLM judge**，这个批评打得没有它自己以为的那么干净。

# 复现
# ClinEnv 复现难度评估

先说结论：**"跑通"不难，"完整复现"很贵，但它可能是目前最值得你投入的一个环境**——因为它正好落在你之前纠结的"程序性/序贯决策"那一支上，而且是少数带确定性奖励的医疗 agent 环境。

## 一、它到底是个什么东西

ClinEnv 把 MIMIC-IV v3.1 + MIMIC-IV-Note v2.2 的真实住院记录自动切成有序的"决策阶段"，模型扮演主治医生，每个阶段必须主动向 patient/nurse/lab/history 四个 agent 提问，然后提交用药、操作、诊断决策。规模是 3,509 例住院、9,297 个决策阶段、26,043 条 ground truth。最强的 GPT-5.4 也只有 0.306 decision F1，其中诊断 0.51、用药 0.097。

## 二、复现难度拆解（从易到难）

**① 数据准入 — 中等阻力，但周期长**
benchmark 发布在 PhysioNet，必须先满足 PhysioNet 合规资质。CITI 培训 + DUA 审批通常 2–6 周。**这是硬门槛，建议今天就去申请**，别等到想跑的时候才发现卡在这。

**② 一个容易被忽略的坑：ZDR 合规**
论文脚注写得很轻描淡写：闭源模型是在 PhysioNet 要求的 Zero Data Retention 政策下访问的。这意味着你不能拿学生号直接调 OpenAI/Anthropic API 去跑 MIMIC 数据——需要企业级 ZDR 协议或 Azure OpenAI 的合规通道。**对研究生这是最实际的障碍**，比算力还麻烦。绕开方式：只评本地开源模型（Llama/Qwen/Gemma 系），这条路完全合规。

**③ 评测端 API 成本 — 这是真正的大头**
算一笔账：GPT-5.4 平均 9 轮/阶段，且后期阶段查询数会爬到 50+ 轮，每阶段上限 60 轮。每一轮信息查询还要触发一次 GPT-5.4-mini 驱动的 agent 应答，再加上 coverage 的 judge 调用、ICD 映射的 LLM reranker。粗算下来评一个模型 ≈ 十万量级的 LLM 调用、10⁹ 量级的输入 token（对话历史每轮重发，成本接近平方增长）。
**务实做法：抽 300–500 例跑**，方差已经够用了，成本降到 1/10。全量 3,509 例除非你要发榜单，否则没必要。

**④ 本地模型推理 — 你的算力约束在这里**
论文评了 Llama-3.1-70B/8B、Gemma-3-27B/12B。8B/12B 单卡能跑；27B 要量化；70B 基本要 2×A100 起步。考虑到多轮长上下文，KV cache 压力比一般 benchmark 大。**建议只做 7B–14B 档 + vLLM，先把 pipeline 跑通。**

**⑤ 从 MIMIC 原始表重建整条构造 pipeline — 不建议做**
构造用 Claude-Sonnet-4.6 做 planner，Phase B 用 20 事件滑窗顺序锚定，预处理版本包含 24,760 个 subject、229,482 个 admission 文件、2.378 亿条事件。光 Phase B 一例住院就可能几十次 LLM 调用。**除非你要改造构造逻辑（比如换成中文 EHR），否则直接用他们发布的 case 文件。**

## 三、复现不出原数字的风险点（提前知道）

用药打分要走 RxNorm API 解析 ATC；诊断/操作要先用 embedding 检索 ICD 全表 top-15 再让 LLM 重排；lab 成本查 CMS 收费表；药费查 NADAC + WHO ATC/DDD。这一串外部依赖里任何一个版本漂移，分数都会变。**你的复现目标应该定成"趋势一致"而不是"小数点后三位一致"。**

还有一个明确的文本 bug 可以留意：效率指标在正文 Eq.12 写的是 `cov / max(1, K/|A_k|)`，附录 C.7 却写成 `cov × N/(N+K)`。**两个公式不等价**。复现时以代码为准，这个不一致本身也值得写进你的 report。

## 四、锐评：值不值得

**值得，但理由不是"复现"，是"占坑"。**

支持的理由：
- 它是**确定性奖励的交互式医疗环境**。用药走 ATC 层级偏序、诊断走 ICD 祖先集 HDF1、Hungarian 匹配——不依赖 LLM judge。这是天然的 RL reward signal，作者自己也在类比 SWE-Gym。你之前担心 RL 后训练不可行，但这里可以先做**推理时方法**（信息获取策略、记忆压缩、query planner），不碰参数也能出结果。
- **天花板极低留出的空间巨大**：0.31 总分、0.097 用药分。这不是"再刷 2 个点"的赛道，是"随便做点像样的东西就能涨"的赛道。
- 它已经开始被引用了（比如 MedBench v5 的 related work 里有它），说明社区在接。

需要警惕的：
- **提交接口泄题**。系统会告诉模型每种类型要交多少条，只暴露 ground truth 中存在的提交工具。这等于告诉医生"你现在该开 2 个药"——现实里没有这个信号。这是他们为了让 Hungarian 匹配在等大集合上跑而做的妥协，但也让任务失真了。**这是你可以攻的点。**
- **"长程"是打折的**。每进入新阶段，环境会把上一阶段的真实 ground truth 决策注入上下文，让后续阶段基于真实发生的事而非模型自己的错误。这是 teacher forcing,不是真正的误差累积。所以"long horizon"更像"长上下文",不是"长决策链"。**要做真正的序贯误差传播,这里有现成的改造入口。**
- **没有人类基线**。0.31 到底是模型差,还是 benchmark 上限本来就低?ground truth 是"主治当时开了什么药",临床等效的替代方案一律算错。作者自己在 Limitations 里承认这衡量的是与真实临床实践的一致性,而非与唯一最优解的对比。**补一个小规模医生基线,本身就够写一篇短文。**
- 过程指标仍然是 LLM-as-judge,"确定性"只覆盖 outcome 那一半。

## 五、建议的推进顺序

1. **今天**:提交 PhysioNet 认证申请（周期最长,先启动）
2. **同时**:找到 GitHub 仓库确认代码是否真的开放——论文 HTML 里那个脚注是占位链接,我没能验证到实际仓库地址,建议直接邮件问一作 Yuxing Lu（北大未来技术学院博士生,GT-Emory-PKU 联合项目,主页 yuxinglu613.github.io,响应通常不错)
3. **拿到数据后**:先用 Qwen/Llama 7B 档 + 抽 200 例跑通全链路,验证打分器能不能复现
4. **然后**:别急着刷分,先挑上面四个软肋里的一个做改造

如果你的目标是**做 agent 而不是做 benchmark**,ClinEnv 的价值在于给你一个免费的、带确定性奖励的训练场——这个价值远大于把表 5 的数字复现一遍。
