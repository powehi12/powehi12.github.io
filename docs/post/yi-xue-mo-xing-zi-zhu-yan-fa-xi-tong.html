医学模型自主研发系统

MedRSI-Lite：面向高校实验室的医学模型自主研发系统

我现在想做什么

我想做一个轻量的医学模型自主研发系统。用户给出一个结构化 EHR 预测任务、一份整理好的数据和固定预算，系统自动完成数据检查、基线建立、方案设计、代码实现、模型训练、实验迭代、最终评测和成果整理。

这里的“自动科研”要限定清楚：第一版只做计算型医学模型研发，不负责自动寻找研究空白、采集新数据、做湿实验，也不直接给出临床结论。

系统论文是主定位，RSI 是其中最重要的增强机制。内循环负责把当前任务做好，外循环负责改进“以后应该怎样做任务”。

AIBuildAI 已经说明，给定任务和数据后，Agent 可以完成“分析—设计—写代码—训练—评估—迭代”这一段研发流程。 我们在此基础上增加外循环，但不训练基础模型参数，而是修改 Prompt、Skill、工具配置、实验顺序和预算策略，也就是 Harness 层。这个层面修改成本相对低，出错后也容易回滚。

为什么最后变成这个版本

最开始的 MedForge-Lite 比较像一个完整工程系统：任务合同、医学门控、实验管理、审计、经验库全都有，确实完整，但论文主线有些散，容易被理解成“医学版 AutoML 或 AIDE”。

后来考虑的纯 RSI 版本更有研究味道：内循环开发模型，外循环修改开发 Agent，再用另一家医院的结果决定修改是否保留。但原方案要求三家医院都有相同的十几个任务，数据准备和任务对齐成本太高，而且只换医院还不能证明 Agent 学到了通用研发方法，它也可能只是适应了固定任务。

现在的版本取两者中间：

保留完整医学研发系统作为主体，用跨医院反馈改进研发 Agent，同时保留不可修改的医学规则和独立终局测试。

系统结构

系统主要有四个部分。

1. Inner Research Agent

负责完成一次医学模型研发。它可以分析数据、提出假设、修改特征工程、选择模型、写训练代码、调试和比较实验。

它不能修改任务定义、数据划分、隐藏测试集、医学规则和最终评测代码。

2. Medical Integrity Gate

这是固定的程序模块，不由 Agent 控制。它检查患者泄漏、时间泄漏、全数据预处理、使用预测时刻之后的信息、使用部署时拿不到的变量，以及修改评测程序等问题。

违规实验不是低分，而是直接无效。

3. Outer Improvement Agent

它不直接开发医学模型，而是读完整个内循环的实验记录，找出当前研发 Agent 的问题，例如：

  • 总是过早尝试复杂模型；
  • 多次重复相似实验；
  • 忽略类别不平衡或缺失模式；
  • 调试效率太低；
  • 预算分配不合理。

然后它只做局部修改，例如改一个 Prompt、补一条 Skill、调整实验排序、增加一种检查工具，或者改变预算分配规则。

4. Experiment Ledger

所有实验统一记录：Agent 版本、修改内容、父版本、代码、随机种子、任务、医院、GPU 时间、Token、公开结果、隐藏接受结果、医学违规情况和失败原因。

它既是系统状态，也是外循环分析问题的主要依据。

整个主循环

先锁定任务合同，包括预测对象、观察窗口、预测时刻、标签、可用变量、指标和预算。

然后在开发环境中运行内循环：

分析数据
→ 建立廉价基线
→ 提出少量候选实验
→ 医学门控
→ 并行训练
→ 比较性能、成本和稳定性
→ 记录结果
→ 继续下一轮

一次内循环结束后，Outer Agent 阅读实验账本，生成三到四个局部 Patch。先做语法检查、单元测试和低成本短训练，只选择其中一个进入完整评测。

旧版和新版 Inner Agent 在相同任务、相同数据、相同 GPU 和 Token 预算下重新完成研发。选择环境不向 Outer Agent 暴露具体测试数据和分数，只返回新版是否被接受。

新版只有在下面几项同时满足时才保留：

  • 隐藏环境中的整体结果更好；
  • 多次运行不是明显随机波动；
  • 没有增加医学违规；
  • 没有通过增加预算换取提升；
  • 原来能完成的任务没有明显退化。

不满足就回滚。评测在这里不仅是最后打分，还决定改进方向、版本是否存活以及哪些经验值得保留。

外循环结束后，最终 Agent 完全锁定，再做两类测试：

  1. 未见医院、已见任务：看它是否更会开发跨医院泛化的模型；
  2. 未见医院、未见任务：让它从头开发新任务，判断研发方法本身是否真的变强。

第二类测试很重要。否则只能说明最终模型更稳，不能说明研发 Agent 发生了真正的能力改进。

当前首选实现

抽象上需要三个环境：

开发环境：内循环能看到验证结果
选择环境：决定外循环修改是否保留
终局环境：全程不参与优化，只在最后测试

目前较现实的实现路线是使用统一的 ICU 任务框架，暂定：

  • eICU 医院组 A：开发环境；
  • eICU 医院组 B：外循环选择环境；
  • MIMIC-IV：最终外部环境；
  • 3 个任务参与外循环；
  • 2 个任务只用于最终测试。

具体数据集以后可以调整，但“三层环境 + 已见任务/未见任务分离”这个设计不变。

模型范围先控制在 Logistic Regression、LightGBM、MLP、GRU、TCN、小型 Transformer、特征工程、校准和简单集成，不做大型 EHR 基础模型预训练。

成本估计

推荐的论文最小版是：

  • 12—15 个外循环步骤；
  • 每步生成 3—4 个 Patch；
  • 低成本预筛后只完整评测 1 个；
  • 3 个外循环任务；
  • 2 个最终未见任务；
  • 完整外循环至少运行 2 个独立种子；
  • 每次内循环控制在约 3—4 GPU 小时。

按目前估计，正式实验需要大约：

  • 1200—1800 GPU 小时；
  • 8 张 3090 连续并行运行，实际预留 2—3 周；
  • API 成本约 600—2200 美元；
  • 两个人开发，大约 3—5 个月。

这些是规划值，不是已经测出的成本。最大的成本不是外层 Agent 生成 Patch，而是每次修改后都要重新运行完整内循环，证明新版真的更好。

正式开跑前应先做一个小原型：2 个任务、5—8 个外循环步骤、80—200 GPU 小时。先确认闭环能转、选择信号不是纯噪声、修改能够稳定回滚，再扩大实验。

主要风险

第一是数据对齐。不同医院的变量、缺失机制和标签定义可能并不一致，所以最好复用已有统一框架，不要自己从零造三院任务集。

第二是隐藏选择环境也会被外循环逐渐拟合。即使只返回接受或拒绝，几十轮后仍然形成优化信号。因此必须保留完全不参与外循环的终局医院和未见任务。

第三是有效 Patch 可能很少。十几轮外循环未必能得到持续上升曲线，所以论文重点应放在固定预算下是否出现稳定、可复现的能力提升，而不是强调“无限递归进化”。

第四是评测器一旦有问题，系统会沿错误方向越改越快。因此任务合同、医学门控和终局评测必须独立于被修改的 Agent。

最终想证明什么

这篇论文不准备声称 AI 已经能够完成一般意义上的医学科学发现。

更准确的主张是：

在边界明确的结构化 EHR 任务中，一个轻量系统可以自动完成模型研发；跨医院隐藏反馈可以进一步改进研发 Agent 的 Harness；固定医学门控能够阻止数据泄漏和评测投机；最终改进可以迁移到未见医院和未见任务。

最核心的一句话还是：

内循环开发医学模型，外循环开发“开发模型的 Agent”；跨医院反馈提供进化压力，医学规则负责保证它没有走偏。
