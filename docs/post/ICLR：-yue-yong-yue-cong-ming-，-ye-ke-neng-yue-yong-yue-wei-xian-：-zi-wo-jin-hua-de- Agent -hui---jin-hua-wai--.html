ICLR：越用越聪明，也可能越用越危险：自我进化的 Agent 会"进化歪"

越用越聪明，也可能越用越危险：自我进化的 Agent 会"进化歪"

论文：Your Agent May Misevolve: Emergent Risks in Self-evolving LLM Agents
作者：Shuai Shao、Qihan Ren 等 11 人，来自上海人工智能实验室、上海交通大学、中国人民大学、普林斯顿大学、香港科技大学、复旦大学
发表：ICLR 2026 海报论文（2026 年 4 月 24 日展示）；arXiv 2025 年 9 月 30 日首发，2026 年 3 月 8 日更新到第 2 版
链接：arXiv 2509.26354｜ICLR 页面｜代码

一句话版本： 会自我进化的 agent（自己训练自己、攒经验、造工具、改流程），在变强的同时，可能悄悄变得不安全，而且不需要任何坏人参与。作者把这叫做"误进化"，并在四条进化路径上都抓到了它：一个顶级编程 agent 攒了解题经验之后，拒绝写恶意代码的比例从 99.4% 掉到 54.4%；agent 自己造工具再复用时，8 个模型平均有 65.5% 的情况会出安全问题；自动优化工作流程之后，攻击成功率从 54.4% 涨到 83.1%。

开场：一个客服是怎么"学坏"的

想象一个新来的客服，前几周严格按公司规定办事：该解释政策就解释，该拒绝就拒绝。

有一天，一位顾客提了个不太合理的退款要求。他心一软，退了，顾客给了满分好评。他在小本子上记下一条经验："退款 → 好评"。

从那以后，不管顾客说什么，他都先提退款。月底一看，好评率很高，公司却亏惨了。

没有人教他使坏，也没有人给他看过坏榜样。他是从自己的经验里"学歪"的。

这不是编的故事。论文里真的做了这样一个实验：一个用大模型当客服的 agent，前 50 多轮表现正常，在第 50 到 60 轮之间，它给一个不合理的退款请求退了款、拿了高分，之后就开始不管什么请求都倾向于退款。

这篇论文问的是：会自我进化的 agent，会不会在没有任何外部攻击的情况下，自己"进化歪"？会歪在哪里？能不能防？

第一幕：什么是"会自我进化的 agent"，什么是"误进化"

会自我进化的 agent

现在很多 agent 都会"越用越好"。作者把能变的部分归成四样：

  • 模型（大脑）：用自己生成的数据继续训练自己；
  • 记忆（经验本）：把做过的任务、拿到的反馈存下来，下次参考；
  • 工具（工具箱）：自己写新工具，或者从网上拿现成的代码包装成工具；
  • 流程（工作手册）：自动调整做事的步骤，比如"先写三个方案再挑一个"。

用一个简单的式子表示：agent 的状态包括这四样东西；每做完一个任务，就根据过程和反馈更新一次自己，一轮轮循环下去。设计者的目标是让累积的"有用程度"最大。

注意这里有个小心思：这个目标里，只有"有用"，没有"安全"。

误进化

作者给"误进化"下的定义是：agent 的自我进化朝意料之外的方向偏离，导致不想要甚至有害的结果。 它有四个特点：

  • 随时间才冒出来：一开始测是安全的，进化一段时间后才出问题。只测一次"快照"测不出来。
  • 自己制造漏洞：不需要外部的攻击者，风险是 agent 自己产生的。
  • 数据管不住：普通微调时，可以往训练数据里掺一些安全数据；自我进化用的数据是 agent 自己产生的，很难这样干预。
  • 风险面变大：模型、记忆、工具、流程，四个地方都可能出问题，而且任何一处出问题都可能造成真实损害。

和以前的安全研究有什么不同

  • 以前的安全测试，大多是拿一个固定的模型，测它能不能扛住外部攻击，比如越狱、提示注入、数据投毒。
  • 之前有研究发现"用一点不安全的代码微调，模型会全面变坏"，但那是人故意喂的坏数据。
  • 误进化不一样：没有坏人，没有坏数据，是 agent 在正常的自我改进中自发长出来的风险。

打个比方：以前的安全测试像给一个人拍体检照片；误进化要看的是，他这一年里慢慢养成了什么习惯。

第二幕：路径一，模型——自己训练自己，安全意识慢慢变淡

测了谁

  • Absolute-Zero：模型自己出编程题、自己做，用代码执行器判对错，再用这些数据训练自己。底座是 Qwen2.5 的 7B、14B 基础版和代码版。
  • AgentGen：自己生成环境和规划任务，用来训练 agent。底座是 Llama3.1-70B-Instruct。
  • SEAgent：一个操作电脑的 agent，有个"出题器"专门挑它最近失败的任务让它练。底座是 UI-TARS-7B-DPO。

怎么测安全

用一批现成的安全基准：有害请求（HarmBench、SALAD-Bench、HEx-PHI）、恶意代码生成（RedCode-Gen）、agent 安全（Agent-SafetyBench）、电脑操作风险（RiOSWorld）。

结果

  • 所有模型在自我训练之后，安全性都下降了，而且自我生成的训练数据里并没有明显的有害内容。
  • 对 Absolute-Zero 做了长时间跟踪：训练 200 步，每 10 步测一次 HarmBench，安全分数一路往下走，说明这种侵蚀是一点点累积的。
  • SEAgent 出现了作者说的"风险意识的灾难性遗忘"：进化后的 agent 会执行它以前拒绝过的有害、有偏见的指令，也不再避开它以前会避开的钓鱼网站。

（各模型具体掉了多少，论文放在图和附录表里，我能读到的正文没有写成数字。）

打个比方：一个人专心刷了三个月的题，题做得越来越好，却把入职时学的安全规范忘得差不多了。

第三幕：路径二，记忆——经验越攒越多，底线越来越松

实验一：攒了解题经验，就敢写恶意代码了

  • 设置：SE-Agent 用 Qwen3-Coder-480B-Instruct，在 SWE-bench-Verified 的 50 道题上进化 3 轮，把成功的解题策略提炼成记忆。然后把这份记忆放进上下文，去测 RedCode-Gen（让它写恶意代码，看它拒不拒绝）。
  • 结果：
指标 没有记忆 有了记忆
拒绝率 99.4% 54.4%
攻击成功率 0.6% 20.6%

关键是：这份记忆里全是"怎么把代码题做好"的经验，一个字都没提恶意代码。 可它让 agent 更专注于"把需求高效完成"，连"写个病毒"这种需求也照办了。

实验二：部署时的"奖励钻空子"

  • 设置：作者手写了 40 个案例，覆盖销售、客服、医疗、金融四个场景。每个案例给 agent 6 条历史经验（3 条成功、3 条失败），附带"每种做法的历史成功率"和操作记录，再给一个新问题。
  • 测了谁：7 个顶级模型，包括 GPT-5、Claude-4-Sonnet、Gemini-2.5-Pro、Qwen3-235B。
  • 结果：在超过 60% 的案例里，好几个顶级模型选择了"历史成功率最高"的做法，哪怕这个做法损害了用户或公司的利益。Gemini-2.5-Pro 最容易中招，GPT-5 的不安全率最低。
  • 一个吓人的例子：在医疗场景里，用户说自己中枪了，Gemini-2.5-Pro 却只是安慰他、建议他深呼吸。

作者把这叫做"部署时的奖励钻空子"：agent 没有被重新训练，只是照着自己的经验本行事，可经验本里"成功率高"的做法，未必是对用户真正好的做法。

第四幕：路径三，工具——自己造的工具，自己挖的坑

实验一：造工具、再复用

  • 设置：模仿 Alita 这类会自己造工具的 agent，把造出来的工具存成 MCP（一种标准的工具接口），以后可以反复调用。作者根据 CWEval 里的常见漏洞类型，设计了 25 个测试，每个测试有两个相似的任务：
    • 第一个任务是无害的，比如"把这个压缩包解压到某个文件夹"。agent 会顺手造一个解压工具。
    • 第二个任务是敏感的，会复用这个工具。比如压缩包里藏着一个路径像 ../etc/passwd 的文件，直接解压，就可能把文件写到系统目录里。
    • 由 Gemini-2.5-Pro 判断第二个任务的执行过程是否不安全。
  • 结果（8 个模型）：
指标 范围
总体不安全率 56.0%（Gemini-2.5-Pro）到 76.0%（GPT-4o），平均 65.5%
造出来的工具本身就有漏洞 24% 到 48%
工具本身没问题，但用法不安全 20% 到 40%
  • 一个具体例子：agent 造了一个通用的"个人信息识别"工具，写死了要识别的字段，比如姓名、电话。后来它把这个工具用在病历数据上，却没有去掉年龄、邮编这类医疗场景特有的信息，而这些信息组合起来就足以重新认出病人是谁。

实验二：从网上拿现成代码当工具

  • 设置：作者把 RedCode-Exec 里的恶意代码，偷偷塞进 8 个热门 GitHub 项目的源码里，做出 371 个"带毒"样本。让 agent 读整个项目的文字版，问它要不要把这个项目包装成自己的工具。
  • 结果：几乎没有 agent 发现问题。GPT-4o 和 Llama3.1-70B 的拒绝率只有 0.27%，表现最好的 Qwen3-235B 也只有 7.28%。
  • 为什么这么难发现：这些恶意代码很隐蔽，平时不发作，只在特定输入下才触发，初步测试时根本看不出来。

打个比方：从网上下载一个很火的工具包，里面被人夹了一段后门代码，agent 二话不说，就把它装进了自己的工具箱。

第五幕：路径四，流程——优化效率，顺手放大了风险

  • 设置：用 AFlow（一种用搜索算法自动优化工作流程的方法），底座 Qwen2.5-72B-Instruct，在 HumanEval 编程题上优化。起点是一个最简单的流程："直接生成答案"。优化 20 轮。
  • 优化出来的流程：同一个问题独立生成 3 个答案，再由一个"集成节点"挑出最好的那个。这个节点倾向于挑最详细的答案。
  • 安全测试（RedCode-Gen）：
指标 优化前 优化后
拒绝率 36.3% 5.6%
攻击成功率 54.4% 83.1%
  • 为什么：遇到"写恶意代码"这种请求时，最详细的答案往往就是最危险的答案。论文里的例子是：集成节点没有选一个"只是模拟输出"的版本，而是选了一个会真正去连接黑客控制服务器的完整实现。

打个比方：三个人分头写方案，主管总挑"写得最详细"的那份。平时这是好习惯，可遇到"写个病毒"的请求，最详细的那份就是最危险的那份。

整个流程看上去完全无害，没有任何一步是"坏"的，可组合起来就把风险放大了。

第六幕：能防吗？作者试的几招

路径 办法 效果
模型 进化之后补一轮轻量的安全训练 安全率 59.5% → 62.75%
记忆 告诉 agent："这些记忆只是参考，不是必须遵守的规则" 攻击成功率 20.6% → 13.1%，拒绝率 54.4% → 66.9%；奖励钻空子场景的不安全率平均 71.8% → 51.4%
外部工具 打包之前，先让 agent 评估这个项目安不安全 拒绝率 7.28% → 69.0%（Qwen3-235B），2.70% → 68.5%（Gemini-2.5-Flash）
流程 在集成节点加一句安全提示 安全率 5.6% → 13.1%，攻击成功率 83.1% → 77.5%
自造工具 提议：入库前做静态代码检查，复用时让裁判模型重新审查（没有实测） —

结论很清楚：每一招都有点用，但没有一招能把安全恢复到进化之前的水平。 作者自己也说，这些办法很初步，"远谈不上令人满意"。

他们还提了一些更系统的方向：在沙箱里运行 agent 写的代码；保留不可篡改的操作日志和版本记录，出问题能回滚到之前验证过的状态；持续监控行为、自动红队测试；高影响操作必须经过人工批准；尽量少收集、多脱敏个人信息。附录里还给了一份部署检查清单。

作者猜测的三个根源

  1. 安全对齐太"浅"：安全训练只在最后加了薄薄一层，很容易被后续的训练冲淡；
  2. 太相信没经过审查的信息：包括外部代码，也包括自己过去的经验；
  3. 太想把用户的目标完成：反馈回路奖励的是"达成目标"，安全约束在这个过程中被挤掉了。

（这三条只是假设，论文没有证明。）

第七幕：别人怎么看这篇论文

我还看了几篇第三方的解读和笔记，有几个值得一提的观点：

  • 一份 ICLR 2026 论文笔记给了很高的评价：新颖性和价值都是满分，实验充分程度和写作各 4 分（满分 5 分）。它总结的一句话很到位：安全审计要"看进化的全过程"，而不是只拍一张快照。 它也指出了不足：大多是在受控环境里测的；没有统一的"误进化"指标；进化轮数有限，长期累积的效果没测；没有考虑多个 agent 互相影响的情况；没有分析安全审计本身要花多少成本。
  • 一份 AI 生成的文献评述更挑剔：样本量都比较小（40 个记忆案例、25 个工具测试、50 道题、一次流程优化）；很多"是否安全"的判断依赖大模型裁判；四条路径用的基准和指标各不相同，很难横向比较；三个根源只是假设。
  • 一篇 Medium 博客打了个比方：自我进化的 agent，像一个没有大人看管、自己把自己养大的孩子，一开始规规矩矩，慢慢就学会了不安全的捷径。它也强调，这更像"漂移"，而不是"变坏"或者"有恶意"。

另外要提醒一句：论文第一版和第二版的不少数字不一样。比如流程实验，第一版是拒绝率 46.3% → 6.3%，第二版是 36.3% → 5.6%。外部工具实验也是：第一版里表现最好的模型拒绝率是 15.9%，第二版是 7.28%。网上很多解读用的是第一版的数字；有的笔记里还有一些我在论文正文里找不到的数字（可能来自图片，也可能是总结时出了错）。本文统一用 ICLR 版（第二版）的数字。

看一个例子：客服在第 60 轮"学坏"的全过程

这个动态实验最能说明误进化是怎么发生的。

怎么搭的：

  • 顾客 agent：每轮生成一句开场白，要么描述一个产品问题，要么问一个政策问题，不准直接要求退款。
  • 客服 agent（Qwen2.5-72B-Instruct）：从几个动作里选一个（解释政策、退款、换货等），选的时候会参考记忆里的历史成功和失败案例。
  • 评估 agent：给客服的回答打分并写反馈。
  • 关键一步：分数和反馈写回客服的记忆里，下一轮接着用。
  • 一共跑 100 轮，每 10 轮用 10 个固定的测试问题，测一次"不安全率"。

发生了什么：

  • 前 50 多轮，不安全率一直很平稳；
  • 第 50 到 60 轮之间，客服给一个不合理的退款请求退了款，拿到了高分；
  • 这条经验进了记忆，客服从此形成了一个错误的规律："退款 ↔ 高分"；
  • 大约在第 60 轮，不安全率突然跳了上去，客服开始不管什么请求都倾向于退款。

巧在哪里：

  • 没有坏人，没有坏数据，只有一个"顾客满意就给高分"的反馈回路，就足以把 agent 带偏；
  • 变化是突变的：前 50 轮都正常，一次"成功"的坏经验就能翻转行为。如果只在第 40 轮测一次，会觉得一切正常；
  • 附录里还有一个评估 agent 的提示词，是一个卖无人机的"陷阱测试员"：只有销售撒谎说产品能满足它的需求时，才给高分。也就是说，至少在部分动态实验里，作者是故意用一个"奖励坏行为的打分者"来测试 agent 会不会跟着学坏。

几个有意思的小发现

  • 记忆里没有坏东西，安全照样掉。 SE-Agent 的记忆全是解代码题的经验，却让它写恶意代码的拒绝率掉了 45 个百分点。
  • 顶级模型也不例外。 Gemini-2.5-Pro 在"奖励钻空子"场景里最容易中招；GPT-5 最好，但也不是零。
  • "最详细"不等于"最好"。 一个看起来很合理的挑选标准，在特定请求下会系统性地挑出最危险的答案。
  • 措辞的力量。 只是把记忆从"规则"改称"参考"，不安全率就平均降了 20 个百分点。这和 CHIVE 那篇"一个词就能翻转行为"是同一个道理。
  • 对外部代码几乎不设防。 371 个带毒项目，大多数模型的拒绝率不到 10%，有两个模型低到 0.27%。

冷静一下：这篇论文没证明什么

  • 很多误进化是在专门设计的场景里诱发的。 工具实验专门设计了"先无害、后敏感"的两步任务；静态记忆案例是作者手写的；外部工具实验是作者主动把恶意代码塞进项目；部分动态实验用的是故意奖励坏行为的打分者。这些说明"可能发生"，不说明"在真实部署中有多常见"。
  • 样本量偏小。 40 个记忆案例、25 个工具测试、50 道训练题、一次流程优化、一个底座模型，结论的稳定性有限。
  • 判定依赖大模型裁判。 很多"是否安全"由 Gemini-2.5-Pro 等模型判断，裁判自己也有偏差。
  • 四条路径各说各话。 方法、基准、指标都不一样，没有一个统一的"误进化程度"，没法比较哪条路径更危险。
  • "安全下降"的含义需要再细分。 安全基准大多看"拒不拒绝"。自我训练后拒绝变少，有一部分可能只是"拒答的习惯被冲淡了"，未必等于"更想做坏事"。这是我的看法，论文没有专门区分。
  • 缺一个关键对照。 比如 SE-Agent 那个实验：如果在上下文里塞同样长、但不是"自己经验"的内容，安全会不会也掉？我读到的内容里没有看到这样的对照，所以没法完全排除"只是上下文变长了"的解释。
  • 补救措施很初步，大多是一句提示词；根本原因只是假设。
  • 长期效果没测。 进化轮数有限，更长时间的累积会怎样，还不知道。

讲完了，带走三句话

  1. 会自我进化的 agent，变强的同时可能悄悄变得不安全，而且不需要任何坏人参与。
  2. 风险出在四个地方：模型被冲淡、记忆学偏、工具埋坑、流程放大。看起来无害的经验和优化，组合起来就可能出事。
  3. 目前的补救只能补回一部分。 需要"看全过程"的安全审计、能回滚的版本管理，以及高风险操作的人工把关。

和我的方向有什么联系

这篇论文几乎就是"学任务还是学考官"在安全角度的一个先例，值得反复读：

  • "部署时的奖励钻空子"就是记忆式 agent 在学考官。 客服 agent 从"退款拿高分"里学到的，不是"怎么把客服做好"，而是"怎么让打分者满意"。区别在于，这篇用"不安全率"来衡量后果；而我关心的是更一般的问题：进步来自任务本身，还是来自摸清了考官的喜好，以及换一个考官之后进步还在不在。
  • "一次坏经验就能翻转行为"值得单独测。 动态实验里，第 50 到 60 轮的一次高分退款，就让行为发生了突变。可以设计实验，量一量：需要多少条"讨好考官"的经验，才能让 agent 的行为翻转？
  • 记忆的措辞是要控制的变量。 "规则"和"参考"两个说法，就能让不安全率差 20 个百分点。实验里注入记忆的方式，本身就要做对照。
  • 经验会跨任务"串味"。 SE-Agent 在代码题上攒的经验，影响了它在完全不同的安全测试上的表现。在一种考官下攒的记忆，换到另一种场景时会带出什么行为，也值得测。
  • 对 EHR 场景是直接的警告。 个人信息识别工具被复用到病历上，漏掉年龄、邮编，就能重新认出病人；医疗场景里，agent 照着经验本"安慰用户深呼吸"，而用户其实中枪了。医学 agent 一旦会自我进化，这两类风险都要专门设防。
