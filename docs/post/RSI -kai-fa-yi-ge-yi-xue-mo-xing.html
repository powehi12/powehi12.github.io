RSI 开发一个医学模型

RSI 开发一个医学模型

摘要

我们想把“AI 自动开发 AI”变成一个医学里的标准任务：让 agent 在固定算力下从零开发 EHR 基础模型，并研究跨医院泛化反馈能否驱动它真正改进“开发模型的方法”，而不是只学会刷 benchmark。

具体来说，本文是参考通用领域 AIDE² 的工作，在医学领域提出一项新任务：给定一份 EHR 数据和一个固定的算力预算，让一个 agent 从零做出一个 EHR 基础模型。

这件事不是做一次就结束。我们把它放进一个双层循环里：内循环 agent 在固定预算内做出一个模型；外循环 agent 依据其他医院的反馈来改写内循环 agent 的代码，让它下一次做得更好。这样一轮一轮下去，改进的是"做模型的方法"。

一、通用领域与医学领域

通用领域的 RSI 工作

我要模仿的是 AIDE²（Weco AI，2026 年 7 月）。它有两层循环：内循环有一个agent，负责针对某个评测把分数往上做；外循环 agent 不断重写内循环 agent 的代码，让它下一次做得更好。

通用领域存在的问题

在很多通用领域的评测里，分数决定一切，但当循环的分数往上涨时，我们不知道系统是真的变强了，还是只学会了应付这套评测。

AIDE² 设两套分数：公开分、私有分。

公开分：只给内循环 agent 看，据此去当优化目标，目的是训出更好的模型。

私有分：由同一个数据集隐藏的部分数据来计算。

不过，私有分的分值不会直接给外循环 agent，这样是为了防止外循环 agent 拿到多个私有分值后进行拟合。私有分只向外循环agent 透露“接受”或者“拒绝”，如果接受，就迭代版本，否则不迭代。AIDE² 的私有分只能防“背测试集”，泛化能力难说。

医学领域的特点

对于通用领域评测的这个问题，医学领域天然可以比较好的解决。

具体来说，在医学领域内，我们将私有分定义为“换一家医院的表现”。这样可以一举两得，从 RSI 的角度来看，这样可以防止循环靠适应评测协议（取巧）来虚假涨分，从医学的角度来看，跨机构泛化本来就是一个非常核心的实用要求。

此外，与通用领域的语言模型相比，医学领域里的任务算力消耗比较小，结构化 EHR 的数据规模和模型规模都小得多。

二、定义任务

最终要交付是一个任务环境和一套规则。

任务规格

任务是什么：在给定的结构化 EHR 数据和锁死的算力预算内，从零做出一个 EHR 基础模型。

给 agent 什么：原始结构化 EHR 数据、评测脚本的接口、算力预算的计量器、训练器 trainer.py

不给什么：基线代码、超参数、数据配比方案、把事件序列切成 token 的方案、架构选择等，这些全部由 agent 自己定，agent 交付的是一份完整的训练代码。

预算怎么锁：按 GPU·分钟计量，超支的运行直接判无效。锁预算很重要，不锁的话 agent 就会多训几轮刷分，没有意义。锁定之后，就迫使 agent 在同样的算力下，尽力去探索更好的方法，做出更好的模型。

两种分数：

层级 用什么数据 谁用它、怎么用 被查询的频率
公开分 同一家医院，EHRSHOT的 15 项任务 内循环 agent 拿它当优化目标，看到的是具体数值 每训完一版 trainer.py 查一次，一次内循环十几次
私有分 另一家医院，同样这15 项任务 外循环 agent 用它判断一次代码改动该不该接受，但只收到"接受"或"拒绝"信息，看不到私有分数值 每步外循环查一次
终裁评测 第三家医院，同样这15 项任务 只在最后比较时用，任何 agent 都读不到 全程只查一次

三、方法

三个核心部件

部件 干什么 谁能改它
训练代码（trainer.py） tokenization、架构、数据流、优化器、训练循环。算力都消耗在这里 由内循环 agent 每次运行重写
内循环 agent (inner_agent.py) 决定下一版 trainer 怎么写、给它分多少算力、读结果、压缩历史 由外循环 agent 重写
评测器 算公开分和私有分 冻结，只读挂载

内循环 agent 写的是模型，外循环 agent 改的是写模型的方法。

内循环：跑一次 ，产出一个模型

跑一次 inner_agent.py ，它会在固定预算内反复调用 trainer.py 多次，最终交付模型，也就是：

写一版 trainer → 跑训练 → 抽表征、看公开分 → 决定下一版怎么改 → 再写一版 …… 直至预算花完，交出公开分最好的那个模型。

外循环：修改内循环 agent 的源码

外循环 agent 拿到 inner_agent.py 的源码，修改一遍，改完之后评估它，整个内循环再重跑几次（压噪音），比较前后两个版本的私有分信息。

外循环根据执行证据包来修改 inner_agent.py 源码，执行证据包有：

  1. 内循环 agent 当前的源代码：inner_agent.py。
  2. 预算账本：每个配置花了多少算力、拿到了多少公开分等。
  3. 失败日志：崩溃、显存溢出、损失发散、超时各出现了多少次，以及原始报错信息等。
  4. 搜索轨迹：试过哪些配置、每个是从哪个配置改来的、公开分的走势，并附上派生统计量，例如从第几次开始就不涨了、试过的配置彼此有多相似（是不是在原地打转）。
  5. 语言模型开销：提示词平均多长、调用了多少次。

外循环 agent 根据这些信息，来决定改进的方向。

四、初步实验设计

四组实验设置

设置 私有分来自哪 用来回答什么
同机构 同一家医院隐藏的患者数据 通用领域的标准做法，作为参照
跨机构 另一家医院的患者数据 本文提出的方案
消融一：不改代码 另一家医院的患者数据 用来证明改代码本身有用
消融二：盲改 另一家医院的患者数据 用来证明改得有依据才有用

同机构和跨机构两组各跑相同步数的外循环，把两组各自得出的最佳方案，同时拿到第三家医院的数据上各考一次。

两个消融实验

消融一（不改代码）：初始版本的内循环 agent，源码一字不改，用和前两组等量的算力跑相同次数的内循环，然后按私有分挑出最好的那个模型。它排除的解释是"提升来自试的次数多，而不是代码改动"。
消融二（盲改）：外循环 agent 照常重写内循环 agent 的代码，用相同的接受拒绝门槛和算力，唯一的区别是拿不到执行证据包，只能看着当前代码盲改。它排除的解释是"提升来自提案数量多，而不是依据起了作用"。
