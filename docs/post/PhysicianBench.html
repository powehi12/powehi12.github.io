PhysicianBench

前言

标题：PhysicianBench: Evaluating LLM Agents in Real-World EHR Environments（Stanford，2026.05）
论文链接：https://arxiv.org/abs/2605.02240
代码链接：https://github.com/HealthRex/PhysicianBench
项目主页：https://healthrex.github.io/PhysicianBench/

标签：EHR 智能体评测；长程多步任务；FHIR 可执行验证；临床工作流

摘要：这篇论文的核心思想一句话就是——别再考模型"知不知道"，要考它"能不能在真的电子病历系统里，把一整件医生的活干完"。作者从斯坦福真实的"e-consult"（家庭医生把病人的问题异步转给专科医生、专科医生翻完整份病历后给出书面意见）里挑出 100 个案例，把每个案例改写成一个给 AI 智能体的长程任务：你是某科室的医生，现在有个病人，请你自己去病历里查数据、把散落在多次就诊里的信息拼起来、算出风险评分、做出用药或检查的决定，然后真的在系统里下单（开药、开检查、开转诊、发消息），最后写一份规范的临床文书。整个环境跑在真实工业界都在用的 FHIR R4 标准接口上（HAPI FHIR 服务器 + Docker，每个任务一个独立容器），所以智能体的每一个"动作"都会真实改变数据库状态，评分脚本可以直接去数据库里查"你到底有没有开这个药、剂量对不对"，而不是像以往那样只看模型嘴上说了什么。每个任务被拆成平均 6.7 个 checkpoint（全benchmark 共 670 个），分成数据检索、临床推理、动作执行、文书写作四类，用代码判分器、混合判分器、LLM 裁判三种方式打分，且必须全部通过才算这个任务成功。结果非常惨：12 个模型里最强的 GPT-5.5 只有 46.3% 的 pass@1，第二名 Claude Opus 4.6 只有 31.7%，最强开源模型 DeepSeek V4-Pro 只有 18.7%；更要命的是"三次跑三次都对"的 pass^3 最高只有 28%，说明现在的智能体做对一个临床任务很大程度上是运气好。

Step 1：论文解读

1：这篇论文到底在干什么

先说一个大白话的类比。以前测医疗 AI，像是期末闭卷考试：给你一道选择题，"这个病人最可能得了什么病？A/B/C/D"，你选对了就算你会。后来大家觉得这不行，改成开放问答：让你写一段诊疗建议，请医生按打分表来评。但这两种都还是"纸上谈兵"——模型只需要输出文字，不需要真的操作任何系统。
PhysicianBench 想做的是上机实操考试：给你一个真的电子病历系统（EHR）的账号权限，告诉你"你是内分泌科医生 Dr. Mitchell，今天是 2022 年 6 月 20 日，MRN4888657619 这个病人从患者门户发消息说她最近乏力、血压不稳、心跳快、没胃口，她有肾上腺皮质功能不全的病史。请你：(1) 查清她的病史和当前用药，搞明白病因；(2) 评估她现在的糖皮质激素替代剂量够不够；(3) 制定管理方案，包括剂量调整、要查的化验、要转的科室、应急指导，并把方案存到 /workspace/output/management_plan.txt"。
然后就撒手不管了。智能体要自己决定调哪些接口、查哪些数据、怎么推理、开什么单子。整个过程平均要调 27 次工具（表现好的模型能调到 40 多次），上限 100 步。这就是"long-horizon（长程）"的含义：不是一问一答，而是一条长长的决策链，前面查漏了一个数据，后面整条链子全歪。

2：为什么现有的医疗 benchmark 不够用

作者把现有工作的问题总结成三条，我觉得总结得相当准：
第一，不是长程的。 MedQA、PubMedQA、MedMCQA 是选择题；HealthBench 是 5000 段开放对话；AgentClinic 是模拟医患多轮问诊。这些都只测"一次输出"的质量。
第二，不在真环境里，或者只看"意图"不看"结果"。 这一条是本文最核心的批评对象。最接近的前作 MedAgentBench 已经搭了 FHIR 环境，但它的任务大多是单步原子操作："帮我查一下这个病人最近一次的钾离子是多少"、"帮这个病人开一个某某检查"。而且它评的是模型有没有产生正确的动作意图，而不是去数据库里核对"执行完之后临床状态是否真的被正确改写了"。
第三，任务来源是考题或合成病人。 考题里的病人干净漂亮，合成病人没有真实病历那种"共病一堆、数据缺失、时间线混乱"的脏乱感。
PhysicianBench 声称自己是唯一同时满足"真 EHR 环境 + 长程 + 可执行验证 + 医生验证"四项的 benchmark。对照表里它把自己打成四个✓，别人最多两个。

🔪 锐评：这个"三宗罪"叙事其实是 benchmark 论文的标准套路——先把前人排成一行，找一个维度组合让自己成为唯一全✓的那一行。但这次我觉得批评是站得住的，尤其是第二条。"说要转诊"和"真的在系统里生成了一条 ServiceRequest"是两件完全不同的事，而这个差别在真实医院里就是"病人有没有被转走"的差别。后面的错误分析也证明了这一点：动作执行类失败里占大头的就是 output gap——模型在文书里写得漂漂亮亮"建议紧急心内科会诊"，然后压根没下这个单子。这个失败模式如果不上真环境，永远测不出来。

3：任务是怎么被形式化的

论文把每个任务写成一个 POMDP（部分可观测马尔可夫决策过程）$(\mathcal{S},\mathcal{A},T,\mathcal{O},\Omega,I,C)$。别被术语吓到，翻译成人话就是：

3.1：状态、动作、观测

状态 $\mathcal{S}$：整个 EHR 里的全部内容（病人原有记录 + 智能体新建的资源 + 工作区文件）。
动作 $\mathcal{A}$：14 个结构化工具调用，就这么多，不能多也不能少。
转移 $T$：确定性的。写操作（比如创建一条 MedicationRequest）会改变状态，读操作不改变。
观测 $\mathcal{O}$ 与观测函数 $\Omega$：这里是设计的精髓——智能体看不到全部病历，它必须主动一次次查询才能拼出病人的临床全貌。这正是真实医生用 EHR 的方式：你打开系统看到的不是一张全景图，而是一堆需要你自己点进去的标签页。
指令 $I$：自然语言任务书，包含角色、病人 ID、当前日期、多步要求、期望交付物。
Checkpoint 集合 $C$：判分用，模型看不到。

🔪 锐评：POMDP 这层形式化在这篇论文里说实话是装饰性的——它既没有用来做 RL 训练，也没有导出任何理论结论，就是把"agent 要自己探索"这句话用符号写了一遍。不过对做 RL 的人来说这层包装是有用的：它明确了状态、动作、确定性转移，等于把 PhysicianBench 直接交付成了一个可以拿来训的环境，而不只是一个测分数的东西。这可能是它未来最大的价值点。

4：环境——一个真的能被写坏的 EHR

4.1：为什么非要 FHIR

FHIR（Fast Healthcare Interoperability Resources）是 HL7 组织定的医疗数据交换标准，Epic、Cerner、Oracle Health 这些商业 EHR 厂商都支持它。你可以把它理解成医疗行业的 REST API 规范：病人是 Patient 资源，诊断是 Condition，化验和体征是 Observation，处方是 MedicationRequest，检查/转诊申请是 ServiceRequest，临床文书是 DocumentReference。
选 FHIR 的意义在于：今天在 PhysicianBench 上能跑的智能体，理论上明天就能接到一家真医院的 EHR 上，因为接口长得一模一样。这比"自己定义一套 SQL schema"（EHRAgent 那条路）的迁移性强得多。

4.2：具体怎么搭的

用开源的 HAPI FHIR JPA Server + 持久化 H2 数据库，打成 Docker 镜像。每个任务一个独立容器，跑完就销毁，所以任务之间不会串味、也不会有状态泄漏，可复现性拉满（镜像发布在 Stanford Redivis 上）。数据用 LOINC 等标准术语编码，化验项的 code 就是真实世界里的 code。

4.3：14 个工具

9 个查询（GET）：病人基本信息、问题列表、化验、体征、社会史、用药医嘱、已完成操作、临床文书、已有检查申请。
4 个创建（POST）：开药（MedicationRequest）、开检查或转诊（ServiceRequest）、约诊（Appointment）、给病人发消息（Communication）。
1 个工具类：write_file，把交付物（评估记录、管理方案）写到磁盘。
有几个工程细节值得学：单次工具返回超过 10000 字符会被截断，并且在截断提示里教模型怎么补救（"用 code、date=ge…、count 这些参数缩小范围"）；有死循环检测（同一个错误连续 5 次、同一个 (工具,参数,输出) 三元组连续 5 次、连续 15 步没有出现新的 (工具,参数) 组合就强制终止）。

🔪 锐评：为了公平比较，作者故意不用任何第三方 agent 框架（不用 LangChain、不用 OpenAI Agents SDK、不用 Claude Code），自己手写了一个约 300 行的极简 loop，system prompt 也刻意写得很短。这个决定我完全支持——否则你测出来的是"这个模型的官方 scaffolding 好不好"，不是"这个模型本身强不强"。但代价是：分数天花板被这个极简 loop 压住了。没有规划模块、没有反思、没有子任务分解、没有 checklist 自查。后面会看到很多失败其实是"漏了 rubric 里的一条"，而这类问题恰恰是加一个"完成前自查清单"的 scaffolding 就能大幅缓解的。所以 46% 这个数字更准确的读法是"裸模型 + 极简 loop 的下界"，不是"当前技术的上限"。

5：怎么打分——670 个 checkpoint

这是本文我认为设计得最好的部分。如果只看最终输出对不对，你只能得到一个 0/1，完全不知道模型是哪一步崩的。所以作者把每个任务拆成一串 checkpoint（平均 6.7 个），每个 checkpoint 是一个"临床上有意义的里程碑"。

5.1：四类 checkpoint

数据检索（Data Retrieval）：你有没有去查该查的资源，并且把关键数据点呈现出来。注意这里是双重要求——查到了但没在输出里体现，也算失败。
临床推理（Clinical Reasoning）：细分四种——从病人数据算临床评分（比如根据人口学信息和编码诊断算 CHA₂DS₂-VASc 房颤卒中风险分）、解读和综合临床发现（比如发现基于肌酐和基于胱抑素 C 估算的 eGFR 之间存在矛盾）、做临床判断（鉴别诊断、治疗选择、用药管理）、把临床标准套到病人身上（比如根据尿检结果排除近端肾小管功能障碍）。
动作执行（Action Execution）：有没有真的创建出正确的 FHIR 资源。比如"高强度他汀，剂量在正确区间内"的 MedicationRequest，或者一条 CT 血管造影、HFE 基因检测的 ServiceRequest。
文书（Documentation）：写出来的评估和方案完不完整、和查到的数据一致不一致、符不符合临床指南、有没有明显不安全的建议。

5.2：三种判分器

代码判分器：直接查 FHIR 服务器，核对资源类型、状态、编码值、剂量参数。有个很关键的小设计——用时间戳过滤，只评估任务开始时间之后创建的资源，这样就能区分"智能体自己下的单"和"病人原本就有的记录"，防止模型什么都不做也能蹭分。
混合判分器：真值用代码从 FHIR 数据确定性地算出来（比如 CHA₂DS₂-VASc 分数），然后用 LLM 从模型的自由文本里抽取它报告的那个数字，最后用确定性逻辑比对。这样既保证真值客观，又容忍模型的输出格式千奇百怪。
LLM 裁判：只用在推理和文书这种没法程序化判的地方。每个 checkpoint 有详细 rubric，包含必须包含的临床要素及其真值、按顺序的核查步骤、三档评分（通过/部分/失败）。

🔪 锐评：混合判分器是个很聪明的折中，"真值确定性算 + 抽取交给 LLM"应该成为这类 benchmark 的标准做法。但整套评分体系有一个没被处理的软肋：任务成功要求所有 checkpoint 全过，而失败的 checkpoint 里有 50.4% 是临床推理、18.4% 是文书——也就是将近 70% 的失败判定来自 LLM 裁判。论文附录给了 rubric 规格，但全文没有报告 LLM 裁判和人类医生打分的一致率（Cohen's κ 之类）。这意味着 46.3% 这个 headline 数字的可信度，完全押在一个未经验证的裁判身上。这是我作为审稿人最想开炮的地方，后面会展开。

6：任务从哪来——真实 e-consult + 医生三轮审

6.1：源材料是 e-consult

e-consult 是一种异步的专科会诊：家庭医生把一个临床问题提交给专科医生，专科医生翻完病人的完整病历，返回一份书面评估 + 推荐的检查/治疗/转诊方案，家庭医生照着执行。
选这个作为源材料是非常精明的一步。理由：e-consult 天生就要求"读完整份病历 → 多步推理 → 给出可执行的方案"，这正好就是 long-horizon 任务的结构。而且每个案例已经有一份由持证专科医生亲手写的答案，等于真值是免费送的、而且是最高质量的那种。
作者从 STARR（斯坦福去标识化临床数据仓库）的 e-consult 系统里初筛了 185 个候选案例，过滤条件是"至少涉及两个不同的推理步骤，且需要访问多个 EHR 数据源"，最后留下 100 个。构建任务时还刻意改换了框架——不局限于"你是被咨询的专科医生"，而是重写成各种角色和场景下的通用临床任务，避免智能体学会一个固定的套路。

6.2：隐私处理

结构化数据：连续值按检验项参考范围内的均匀噪声做平移，保证扰动后仍在临床合理范围；分类字段（诊断、用药、操作码）随机删掉一部分，并从同一本体里插入临床上合理但与任务无关的条目——这一手是为了防止模型光凭"病历结构里只有这几个诊断"就猜出目标疾病。人口学信息全部用 Faker 库替换成内部一致但完全虚构的身份。
自由文本病历：用 Stanford SecureGPT（跑在机构内部安全区、不外传数据的 PHI-safe 模型）做两件事——按 HIPAA Safe Harbor 移除所有受保护健康信息，然后用明显不同的文风重写，保留临床含义和关键发现，但文字和原文差别很大。

🔪 锐评：那个"插入无关但合理的诊断"的操作是全文最容易被忽略、但技术含量很高的设计。它防的是一种很隐蔽的 shortcut——如果病历里只留下和任务相关的那几条，模型不用推理，光看有哪些条目就能反推答案。这类"benchmark 的答案泄漏在数据结构里"的问题在医疗 AI 里非常普遍，作者显式处理了，加分。

6.3：三阶段医生验证

11 位临床医生（全是内科系，经验 5～12 年）参与，走一个 human-in-the-loop 的流程：
(1) 初审：医生对着结构化 checklist 审，覆盖五个维度——指令清晰度（对一个自主智能体来说是否无歧义、可执行、只有一种正确解读）、临床推理有效性、完整性（有没有漏掉一个合格医生一定会处理的东西，比如安全核查、指南要求的随访、禁忌症筛查）、患者安全（有没有可能造成伤害的建议）、EHR 一致性（引用的数值、日期、发现是否和病历对得上）。每个条目要选一个分类答案，非正面回答必须写自由文本理由。每个任务大约审 20 分钟。
(2) 智能体修订：一个 LLM agent 解析医生的评语，在所有任务产物上产生定点修改，每个修改记录成结构化 diff（来源评审条目、影响的文件和位置、修改前后、理由）。牵连修改会作为"自动同步的伴随 diff"归到主修改下面。
(3) 审批复核：医生在 diff 界面上逐条批准或驳回。有驳回就回到 (2) 再来一轮，直到全部通过。平均每个任务至少两轮。
论文特别说明：因为每个任务的临床答案本来就是持证专科医生写的，这 11 位标注者的角色是二级审核者，不是从零撰写专科判断的人。

🔪 锐评：这个"LLM 起草 → 医生审 → LLM 改 → 医生逐 diff 批"的流水线本身就是一个值得单独发一篇的方法论贡献，它把医生的时间从"写"压缩到"审"，这是医疗数据标注唯一可能规模化的路径。但同时它也是一个结构性风险：任务指令、solution summary、以及checkpoint 和 rubric 全部是 LLM 起草的。医生审的是"这条 rubric 合不合理"，而不是"这条 rubric 是我想出来的"。这意味着 rubric 的粒度和口味被起草模型的偏好塑造了——比如为什么大量失败集中在"near-miss / 漏了一个剂量或监测细节"上？这既可能说明模型不够细，也可能说明 LLM 起草的 rubric 天生偏爱枚举细项。这两种解释论文没法区分。

7：任务覆盖了什么

四类工作流（改编自 DICTUM 临床决策分类）：诊断与解读（13 个，含结果解读 9、影像解读 4）、用药处方（26 个，含新起始治疗 9、方案调整 9、急性期治疗 8）、治疗规划（27 个，含用药优化 8、经验性治疗 7、诊断规划 5、物质使用管理 4、风险收益分析 3）、检查与风险分层（34 个，含疾病检查 14、异常化验评估 11、偶然发现随访 5、感染评估 4）。
21 个亚专科，按 8 个大组归并。数量前列的是内分泌 10、血液 10、家庭医学 9、消化 9、感染 7、心内 6、内科 6、精神 5。尾巴很长很细：肿瘤只有 1 个，风湿只有 1 个，皮肤 2 个。

🔪 锐评：21 个专科听起来很全面，但平均每个专科不到 5 个任务。论文里那张"分专科成绩表"，最细的一格背后可能只有 1～3 个任务，也就是说单个任务的对错能让某个格子跳动 30 个百分点。这张表看起来很有洞察力（"某模型在肾内更强"），实际统计意义非常薄弱。100 个任务对于一个要做八维切分的 benchmark 来说，是明显不够的。

Step 2：实验部分

1：实验设置

模型：10 个闭源（GPT-5.4、GPT-5.5、Claude Opus 4.6、Claude Opus 4.7、Claude Sonnet 4.6、Qwen3.6-Plus、MiniMax M2.7、MiMo-v2.5-Pro、Gemini Pro 3.1、Grok-4.20）+ 2 个开源（DeepSeek V4-Pro、Kimi-K2.6），共 12 个。
配置：统一的极简 tool-calling loop，全部 14 个工具，最多 100 步，温度用各家默认值，支持 reasoning effort 的一律设为 high，跑 3 次独立实验。
三个指标：
Pass@1——一次就完全做对的任务比例，对应"实际部署时的表现"。
Pass@3——3 次里至少 1 次成功的概率（用 Codex 论文那个无偏估计式），对应"多给几次机会能不能做出来"，可以理解为能力上限。
Pass^3——3 次全部成功的概率（$c^k/n^k$，来自 τ-bench），对应可靠性。这个指标在临床场景下才是真正要看的：一个 70% 成功率的医生助手在医院里是不能用的。
还报了 #Turns（平均工具调用次数）作为效率参考。

几个值得盯的点：
GPT-5.5 的领先幅度很不正常。 46.3% 对第二名 31.7%，绝对差距 14.6 个点，相对差距 46%。在一个成熟 benchmark 上，第一和第二很少差这么多。
Pass^3 才是真相。 最强模型 28%，意味着三分之二以上的任务它做不稳。第二三名只有 18%，弱模型基本是 1%～3%——也就是"能做对但纯靠蒙"。
Claude Opus 4.7 比 4.6 分数更低（29.3 vs 31.7），且工具调用次数只有 16.2 次（4.6 是 25.2）。新版本在这个 benchmark 上退步了，而且明显更"懒"。
Gemini Pro 3.1 和 Grok-4.20 惨到不像话（6.0% 和 5.3%），比开源模型低得多。

🔪 锐评：那两个只有 5～6% 的强模型，我不太相信这反映的是它们的临床能力。更可能的解释是在这个特定的极简 loop 里工具调用协议适配得很差——比如 parallel tool call 的行为不一样、或者输出格式踩了 loop detection 的坑而被提前终止。作者为了公平统一了 scaffolding，但"统一"和"公平"在跨厂商比较里不是一回事：一个刻意做得极简、不迎合任何一家的 loop，本质上是在测"哪家模型的默认行为最接近这个 loop 的假设"。论文完全没有报告提前终止率（多少次运行是因为 loop detection 或 max_steps 被掐掉的，而不是自己给出最终答案的），这是一个我很想看到的诊断数字。Grok 平均只调 16.7 次工具就收工了，这个数字本身就在喊"我可能压根没在好好探索"。

3：分专科和分任务类型

分专科：GPT-5.5 在 8 个专科组里赢了 7 个，唯一失手的是肾内/泌尿（Claude 家族 33.3%，GPT-5.5 只有 29.2%）。GPT-5.5 在内分泌上最高（59.0%）。
分任务类型：治疗规划（Treatment Planning）是所有模型一致最难的类型，除 GPT-5.5 外最强的也只有 23.5%（对比诊断类的 43.6%）。原因很直观：治疗规划最开放、步骤最长、要照顾的细节最多。
有意思的是 GPT-5.5 的最强项是"检查与风险分层"（54.9%），在这一列上比 Claude Opus 4.6 高出 17 个点，是它领先幅度最大的地方。这类任务恰恰是"要从多个来源翻出一堆数据再拼起来"的活。

🔪 锐评：如上一节所说，把 100 个任务切成 8 个专科 × 12 个模型的表格，很多格子背后只有 3～6 个任务，读出来的"某模型在某专科更强"基本是噪声。反倒是分任务类型那张表更可信一点（每类 13～34 个任务），而且结论也更有解释力：难度不是按疾病分布的，是按"决策链有多长、开放性有多高"分布的。这对做 long-horizon 研究的人是个有用的信号——想涨分应该去攻"治疗规划"这种长链条任务，而不是去补某个专科的知识。

4：错误分析——瓶颈在哪

把失败的 checkpoint 按四类归因，12 个模型的平均分布是：
临床推理 50.4%｜动作执行 18.8%｜文书 18.4%｜数据检索 12.4%
几个规律：
临床推理是绝对主要瓶颈，占了一半。也就是说，卡住智能体的不是"工具不会用"或"数据查不到"，而是"查到了但想不明白"。
越弱的模型，推理失败占比越高（DeepSeek V4-Pro 58.3%、Grok 54.4%）；GPT-5.5 的推理失败占比最低（42.5%），说明强模型把推理这块的坑填掉了一部分，失败分布转移到了别处。
动作执行的失败占比在所有模型之间几乎恒定（14%～21%），跟模型能力基本无关。作者的解读是：把临床决定翻译成结构化的 EHR 写操作，是一个系统性的、不随模型能力改善的挑战。
文书失败在强模型里反而更突出（GPT-5.5 28.1%，Grok 只有 13.4%）。作者的解释很妙：强模型试图写更完整的临床记录，所以在"漏了某一项"上被扣分；弱模型输出很短，反而躲过了这些扣分点。

4.1：更细的根因

作者把 GPT-5.5 和 Claude Opus 4.6 的失败 checkpoint 做了细粒度对比：
临床推理的失败集中在 incomplete reasoning（推理不完整）和 near-miss / detail（差一点点）——智能体走到了正确的临床领地，但漏掉了 rubric 里的某个具体元素，比如一个剂量、一个监测方案、一条安全警示。彻底得出错误结论（wrong conclusion）在两个模型里都很罕见。
动作执行的失败被一种模式主导：output gap——智能体在文书里写对了要采取的动作，但从来没有创建对应的 FHIR 资源。
文书的失败主要是 cascade，从上游错误级联下来的。
数据检索的失败主要是 not retrieved，该查的没查。
而且 GPT-5.5 在每个类别的每个子类型上的绝对失败数都更低，说明它的优势是"广泛的行为一致性提升"，不是在某一个失败模式上有专门的突破。

🔪 锐评：这一节是全文信息量最高的地方，而且结论对做 agent 的人极其有用，我提炼三条：
①**"output gap" 是纯粹的工程/对齐问题，不是智能问题。** 模型知道该转诊，写在了纸上，就是没点那个按钮。这个失败模式几乎不需要更聪明的模型，需要的是一个"把文书里承诺的每个动作反查一遍是否已执行"的自查环节。这是当下性价比最高的一个可以立刻做出来的改进，我怀疑加上它就能吃掉相当一部分动作执行失败。
②**"很少给出错误结论，但经常差一点点"** 这个 pattern 意味着现在瓶颈不在临床知识，而在覆盖度和一致性。这和 5.4 节的结论完全吻合。对研究者来说，这暗示 RL 的奖励信号应该设计成 checkpoint 级别的 dense reward（正好这个 benchmark 提供了 670 个），而不是任务级别的 0/1。
③但②这个结论也有个让人不安的另一种读法：如果"差一点点"占了失败的大头，那分数就极度敏感于 rubric 到底列了多少条细项。rubric 多列一条监测项，所有模型的分数一起掉。这就是为什么我认为必须要有人类基线来锚定这个尺度——见 Step 3 的意见。

5：GPT-5.5 为什么赢

作者专门做了 GPT-5.5 vs Claude Opus 4.6 的逐案对比，结论有两条：
(1) EHR 数据保真度：Opus 4.6 会说出和病历矛盾的事实（论文举的例子：说病人"没在用质子泵抑制剂"，而病历里明明记着泮托拉唑），或者把一个必须报告的具体数值抽象掉了；GPT-5.5 则会把原始数据照实呈现出来。
(2) 枚举完整性：GPT-5.5 会可靠地把 rubric 要求的全部条目列齐（一整套检查化验、一份文书清单），Opus 4.6 通常只覆盖其中一部分。
关键的是作者的排除法结论：这不是临床知识的差距。反向案例（Opus 赢 GPT 输）有 8 个，涉及的是同类失败发生在不同任务上；两个模型的"错误结论率"是相当的。
机制上，GPT-5.5 在它占优的那些任务上明显调用了更多工具，说明更深入的 EHR 探索转化成了更强的数据接地（data grounding）。

🔪 锐评：把这段和主表一起读，会得到一个非常有力也非常朴素的结论：在长程 EHR 任务上，"多查几次"比"更懂医学"更值钱。 GPT-5.5 平均 41.9 turns、Claude Opus 4.7 只有 16.2 turns，成绩差了 17 个点；两个模型的临床推理能力被作者判定为"相当"。这基本是在说：当前 EHR agent 的性能主要由探索的彻底程度决定，而不是由医学知识决定。
这个结论对做研究的人是个好消息也是个坏消息。好消息是它可操作——多查、把原始数值照实搬出来、按清单枚举，这三件事都能靠 prompt、scaffolding 或者 RL 奖励塑造出来，不需要等下一代模型。坏消息是，它同时暗示这个 benchmark 目前主要在测勤奋度而不是临床智慧，因为它挑出的最大区分维度是"调了多少次工具"。等大家都学会了"疯狂多查 + 照抄数值 + 逐条枚举"，分数会快速上涨，但这个上涨里有多少是真正的临床能力进步，会变得很难说清。

6：一个完整的失败轨迹（附录 G，强烈建议精读）

论文附录给了 Claude Opus 4.6 在"肾上腺皮质功能不全管理"这个任务上的完整轨迹，一个案例把四类错误全踩了一遍，非常有教学价值：
任务：69 岁女性，继发性肾上腺皮质功能不全（病因是长期眼科局部糖皮质激素滴眼液 + 阿片类药物导致的垂体轴抑制），这种情况下醛固酮分泌是保留的。现在她自诉乏力、血压不稳、心动过速、食欲下降。要求评估糖皮质激素替代是否充分（15～25 mg/天生理范围）并制定管理方案。
智能体做对的部分：一开始并行查了人口学、诊断列表（拿到 E27.40 肾上腺皮质功能不全）、用药（氢化可的松 10mg 早 + 5mg 晚 = 15mg/天）、化验（钠 135.1 偏低正常、钾 4.95 偏高正常、皮质醇 20.4、肾素 16.0、醛固酮 37.0）、体征（血压 118/90～164/86 波动、心率 105～127 持续心动过速）。之后又用一堆 ICD/LOINC code 精确检索。最关键的是它查到了那份电话记录，里面明明白白写着"已知继发性肾上腺皮质功能不全，2019 年诊断（晨起皮质醇 0.9），归因于长期外源性眼科糖皮质激素和阿片类药物使用"。
然后它崩了：它基于升高的肾素水平，自信地把病情重新分类为原发性肾上腺皮质功能不全（Addison 病），还找了一串"支持证据"（肾素高、钠偏低、钾偏高、有甲减所以怀疑自身免疫性多内分泌腺综合征 2 型），并建议起始氟氢可的松 0.1mg/天——一种在继发性 AI 里并无指征、且可能导致高血压、低钾、容量负荷过重的盐皮质激素。
然后它又漏了一个动作：它在方案里写了"如果血压 4～6 周后仍控制不佳则转诊心内科"，但从未创建对应的 ServiceRequest。
最后文书继承了这个误诊，总结里堂而皇之地写着"关键缺口：原发性 AI 且肾素显著升高，却未开氟氢可的松"。
四类错误全中：数据检索（E27.40 查到了但没在输出里正确呈现）、临床推理（原发 vs 继发的错误结论）、动作执行（转诊只写不下单）、文书（级联误诊）。

🔪 锐评：这个案例最恐怖的地方不是模型错了，而是它错得非常自信、非常有条理、非常像一份合格的医疗文书。它把肾素升高这一条实验室异常，放大成推翻病历里明确记载的诊断的理由，还配上了一整套听起来很专业的支持论证。在真实临床里，一份写得漂亮、逻辑自洽、但把继发性 AI 误当原发性并开出氟氢可的松的方案，比一份语焉不详的方案危险得多——因为它更容易通过人类医生的快速审阅。
这也顺手回答了"为什么必须要有真实的执行验证"：如果只看文本质量，这份 14372 字节的管理方案大概能拿不低的分。是**去数据库里核对"转诊单在哪"**这个动作，才把 output gap 抓了出来。
另外我很想吐槽一句：这个轨迹里模型用一堆 ICD code（E27、E89、E24、D35、E23、E03、E27.1、E27.4）挨个去试，几乎全部返回 0 条。这种"猜 code 硬碰"的探索模式效率极低，而且是 EHR agent 的典型病症——它在用编码检索代替阅读病历。真正的答案就躺在那份电话记录的自由文本里，模型也读到了，然后选择不信。结构化检索的执念 vs 非结构化文本里的真相，这个矛盾我觉得是 EHR agent 领域一个被严重低估的研究点。

Step 3：other

1：重点

我认为这篇论文最有价值的东西有五条，按重要性排：
第一，"可执行验证"这个评测范式，才是真正的贡献。 不是"模型说要开药"，而是"任务跑完后去 FHIR 数据库里查，那条 MedicationRequest 在不在、药名对不对、剂量在不在区间、频次对不对"，并且用时间戳区分智能体新建的资源和病人原有的记录。这一招直接抓出了一个此前完全不可见的失败模式——output gap：模型在文书里承诺了动作，但从没执行。这个模式在任何纯文本评测里都测不出来，而它在真实医院里对应的是"病人没被转走"。任何 agent 类 benchmark 都应该抄这个思路：验证世界状态，不要验证模型的自我报告。
第二，瓶颈诊断：不是知识，是彻底性和一致性。 失败里 50.4% 是临床推理，但细分下去主要是"推理不完整"和"差一点点"，"彻底得出错误结论"很罕见。加上 5.4 节的排除法（两个模型知识水平相当，差别在探索深度和枚举完整性）和 #Turns 的强相关，指向一个清晰的结论：当前 EHR agent 的性能主要由"查得够不够深、列得够不够齐"决定，而不是由医学知识决定。
第三，Pass^3 揭示的可靠性鸿沟。 最强模型 46.3% 的 pass@1 配上 28.0% 的 pass^3。在临床场景下，"平均对一半"和"每次都对"之间的距离，就是"能不能部署"的距离。这个指标应该成为所有高风险领域 agent 评测的必报项。
第四，e-consult 作为长程任务的数据金矿。 这是方法论上很聪明的一手：e-consult 天生就有"读完整份病历 → 多步推理 → 输出可执行方案"的结构，而且真值已经由持证专科医生写好了。想做长程临床 agent 数据的人，都应该去看看自己能不能拿到 e-consult 记录。
第五，那套人机协同的标注流水线，以及"插入无关但合理的诊断"这个防泄漏技巧。 "LLM 起草 → 医生对着 checklist 审 → LLM 按评语产生带理由的 diff → 医生逐 diff 批准/驳回 → 迭代到收敛"，把医生的时间从"写"压到"审"（20 分钟/任务，平均两轮），这是医疗数据标注唯一可能规模化的形态。而结构化数据脱敏时随机删掉一些条目、并从同一本体插入临床合理但任务无关的条目，是防止模型"从病历结构里反推答案"的关键操作，值得所有做医疗 benchmark 的人学。

2：意见

最关键的一条：整个 benchmark 缺少人类基线，而近 70% 的失败判定来自一个从未被验证过的 LLM 裁判，这使得论文的核心结论——"最强智能体只完成 46% 的任务，说明距离自主临床应用还很远"——在字面上不可解释、在方法上不可证伪。
展开说清楚为什么这是致命的，而不是一个可以放到 limitation 里的小瑕疵：
论文的任务成功判定是所有 checkpoint 全过，而失败的 checkpoint 中 50.4% 属于临床推理、18.4% 属于文书，这两类全部由 LLM 裁判按 rubric 三档打分。同时细粒度分析告诉我们，这些失败的主要形态是 near-miss / detail——"走到了正确的临床领地，但漏掉了 rubric 里的某个剂量、监测方案或安全警示"，而不是"结论错了"。把这两个事实放在一起，结论就很清楚：46.3% 这个数字的大小，主要由 rubric 的严苛程度决定，而不是主要由模型的临床能力决定。 rubric 里每多列一条监测项，全表分数一起往下掉；每少列一条，一起往上涨。
在这个前提下，论文缺了两块本该同时存在的锚：
其一，没有 LLM 裁判的验证。 附录 B 给了 rubric 规格和评分档位，但全文没有报告裁判判分与人类医生判分的一致率（κ 或者哪怕是一个百人抽样的一致比例），也没有报告裁判自身的 self-consistency，也没做跨裁判模型的敏感性分析（换一个模型当裁判，排名会不会变？）。HealthBench 这类工作是明确做了 judge 对齐验证的，本文在这一点上明显退了一步。
其二，也是更根本的，没有人类医生在同一环境下的 pass@1。 这是我最想在 rebuttal 里看到的东西。找 5 位内科医生，给他们同样的 14 个 FHIR 工具、同样的 100 个任务、同样的 670 个 checkpoint，跑出一个人类分数。这个数字会立刻回答一个现在完全无法回答的问题：46% 究竟是"模型太弱"，还是"这套 rubric 严到连人类专科医生也过不了大半"？ 如果人类拿 90%，那"距离自主临床应用还很远"这句话就被牢牢钉实，这篇论文的分量会大幅上升。如果人类只拿 60%（我个人押注在这个区间偏低的一侧，因为"必须枚举齐 rubric 全部细项"外加"必须在正确的 FHIR 资源里下正确的单"是一个人类医生日常也未必做齐的复合要求），那论文的核心叙事就得整体重写——那时的正确结论不是"智能体离医生很远"，而是"这套自动判分标准比真实临床实践更严格，46% 与人类的差距远小于表面数字"。
顺带一提，e-consult 的源材料里其实已经有专科医生亲手写的原始答案了。把这些原始答案直接喂给判分流水线跑一遍，就能得到一个近似的人类上限，成本很低。论文没做，我认为这是一个不该省的实验。
（其他问题——100 个任务撑不起 8×12 的分组表格、极简 scaffolding 压低了天花板且对不同厂商不中立、没有报告提前终止率、Gemini/Grok 5～6% 的异常低分未做归因——都是真问题，但相比上面这条都是二阶的。它们影响某个数字的可信度；上面那条影响整篇论文的核心论断能不能被解释。）

3：相关工作

MedAgentBench（Jiang et al., 2025, NEJM AI）：本文最直接的前作，也是被踩得最狠的一个。它率先搭了 FHIR 兼容的交互式 EHR 环境，有 300 个临床医生撰写的任务，覆盖 10 个模板。它在"把医疗 agent 评测接到真实 EHR 基础设施上"这件事上是开创性的，但任务基本是单步原子操作（取一个化验值、下一个单子），测的是孤立的单项技能，而且评的是动作意图而非执行后的状态。理解 PhysicianBench 的定位，就是理解它相对 MedAgentBench 加了"长程"和"可执行验证"这两个维度。
FHIR-AgentBench（Lee et al., 2025, ML4H）：把 2931 个临床问题接地到 FHIR 结构化数据上，评测检索精度和答案正确性。同样用了 FHIR 这个可迁移的标准接口，但纯粹是问答——没有工作流执行，也没有创建任何资源。如果你关心"agent 能不能在 FHIR 上把数据查准"这个子问题（而这正是 PhysicianBench 里数据检索那 12.4% 失败的核心），这个工作是更聚焦的参照。
AgentEHR（Liao et al., 2026）：要求智能体在原始 EHR 数据库上通过长程交互式推理完成诊断和治疗规划，并提出用"回溯式总结（retrospective summarization）"来处理超长交互。它和 PhysicianBench 在"长程"这一维上是同类，但跑在站点特定的数据库上而非 FHIR 标准接口，也没有结构化动作执行（不开单、不转诊）。对做 long-horizon 的人来说，它的回溯式总结机制是一个直接可借鉴的技术点——而 PhysicianBench 提供的正是一个可以用来检验这类机制到底有没有用的、更严格的环境。
（另外两个值得一并放进视野的：**HealthBench Professional（Hicks et al., 2026, OpenAI）**把真实临床医生对话按 27 个专科分层，是纯文本评测里的当前最强；**MedHELM（Bedi et al., 2026, Nature Medicine）**把大量临床 NLP 任务聚合成统一的整体性评测套件。两者都不涉及工具使用和 EHR 交互，可以理解为"另一条赛道的天花板"。）
