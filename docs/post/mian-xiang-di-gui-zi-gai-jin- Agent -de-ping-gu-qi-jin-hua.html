面向递归自改进 Agent 的评估器进化

摘要： 自改进 Agent 会不断生成新版本，通常测试分数更高就能迭代。但新版本可能没有真正变强，只是摸清了当前判分程序的漏洞。我们的做法是让多套判断方式不同的评分器共同把关，并把它们发现的争议案例继续用来修补和扩充评分器，让评估环节也能逐步改进。

问题在哪

自改进系统通常很直接：Agent 修改自己的提示词、工具或代码等等，跑一遍测试，分数比旧版本高，就让它成为下一代。

问题是，分数提高不一定等于能力提高。

新版本可能真的把任务做得更好了，也可能只是发现了判分程序的特殊习惯。比如它知道评分器只检查最终文件、不检查中间过程。候选只要顺着这些细节调整行为，就可能拿到更高分。

隐藏测试集不能解决这个问题。隐藏测试只是换了一批题，但如果新题仍由同一套程序判卷，候选对评分程序的适应仍然有效。

也就是说，现有系统通常只检查：

换一道题，它还会不会？

但没有检查：

换一台判卷机，它还会不会？

还有一个更长期的问题。就算一开始准备了几套不错的评分器，Agent 经过几十轮修改后，也可能逐渐找到它们共同没有覆盖的角落。Agent 在持续进化，评分器却一直不变，评估环节迟早会落后。

我们想怎么做

整个想法可以理解为两件事：先让不同的评分器一起把关，再让评分器根据争议案例继续改进。

第一步，准备几种真正不同的判法。

这里可以让评分器从不同角度检查结果。

比如一套评分器直接检查最终输出；一套调用独立参考程序重新计算；一套查看执行记录，确认 Agent 是否真的完成了必要操作。

但这还不够。我们会拿一批正确结果，故意制造各种错误版本，比如删掉字段、改错数值、截断输出、只完成一半，看看每套评分器分别能发现哪些问题。

如果两套评分器总能发现完全相同的错误，它们其实没有提供多少额外信息。只有判断正常结果比较可靠，又能补上现有评分器盲区的新评分器，才会进入隐藏评分器池。

第二步，用这些评分器决定候选能不能迭代。

Agent 在开发阶段只能看到日常使用的任务和评分器。候选版本提交后立即冻结，不能再修改，也不知道迭代检查会抽取哪些隐藏任务和评分器。

系统让候选版本和当前版本完成同一批任务，再交给几套隐藏评分器分别判断。我们关心的是：

这些不同判法是否都认为候选比旧版本更好？

几套评分器结论基本一致，候选可以升级；都看不出可靠提升，候选被拒绝；如果有的说它明显变好，有的却说它变差，候选先进入隔离区，不直接成为下一代。

第三步，把评分器分歧变成新的测试材料。

进入隔离区后，系统会进一步确认问题出在哪里：是候选利用了评分漏洞，还是某套评分器自己判错了。

确认后，系统而会围绕它生成一批相近情况。既包括错误结果，也包括形式不同但仍然正确的合法结果。

这样做是为了避免评分器走向另一个极端：为了堵住一个漏洞，干脆把所有稍有变化的输出都判错。

第四步，修补和扩充评分器。

这些争议案例会被用来修补旧评分器，或者生成新的检查方式。

新评分器不能因为解决了刚刚那个案例就直接上线。它还要证明三件事：原来判断正确的地方没有被破坏，合法的新表达不会被大量误杀，并且它确实能发现现有评分器遗漏的问题。

通过检查后，它才会在下一轮加入评分器池。

整个过程中，有一条规则保持不变：**什么结果算正确，由固定的任务契约决定。**评分器可以越来越会判，但不能自己把正确答案的定义改掉。
